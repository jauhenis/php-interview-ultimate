# Composer и инструменты PHP

[Документация Composer](https://getcomposer.org/doc/)

Это руководство посвящено Composer 2 и инструментам, которые обычно устанавливают в PHP-проект через него.

## `composer install` и `composer update`

- **`composer install`** читает `composer.lock` и устанавливает ровно те версии, которые в нём указаны. Если lock-файла нет, команда работает как `update` и создаёт его.
- **`composer update`** игнорирует lock-файл, подбирает самые новые версии, допустимые ограничениями в `composer.json`, и записывает новый `composer.lock`. `composer update vendor/package` обновляет только указанный пакет.

Используйте `install` в CI и на проде, а `update` — только когда действительно хотите сменить версии зависимостей.

## Ограничения версий

Composer следует семантическому версионированию: `MAJOR.MINOR.PATCH`. Мажорный релиз может ломать обратную совместимость, минорный добавляет возможности, а патч исправляет ошибки.

| Ограничение | Допустимые версии |
| --- | --- |
| `1.2.3` | ровно `1.2.3` |
| `^1.2.3` | `>=1.2.3 <2.0.0` |
| `^0.3` | `>=0.3.0 <0.4.0`, потому что в `0.x` любой минорный релиз может ломать совместимость |
| `~1.2` | `>=1.2 <2.0` |
| `~1.2.3` | `>=1.2.3 <1.3.0` |
| `1.*` | `>=1.0 <2.0` |

`^1.0 || ^2.0` принимает любой из двух диапазонов. `^` — рекомендуемый вариант по умолчанию для большинства зависимостей.

## `require` и `require-dev`

- **`require`:** пакеты, нужные приложению во время работы: фреймворк, HTTP-клиент, ORM.
- **`require-dev`:** пакеты для разработки и CI: PHPUnit, PHPStan, PHP-CS-Fixer. Пакет добавляется через `composer require --dev vendor/package`.

`composer install --no-dev` пропускает `require-dev` и `autoload-dev`: `vendor/` становится меньше, а поверхность атаки на проде — уже. Composer устанавливает dev-зависимости только корневого проекта, но никогда — dev-зависимости установленных пакетов.

## Папка `vendor`

Composer устанавливает пакеты в `vendor/` и генерирует `vendor/autoload.php`. Добавьте `vendor/` в `.gitignore`: `composer.json` и `composer.lock` полностью её описывают. Не редактируйте файлы в `vendor/`: следующая установка их перезапишет. Чтобы исправить ошибку в зависимости, отправьте исправление в исходный репозиторий, используйте форк или примените патч через `cweagans/composer-patches`.

## Автозагрузка

```json
{
    "autoload": {
        "psr-4": { "App\\": "src/" },
        "classmap": ["legacy/"],
        "files": ["src/helpers.php"]
    },
    "autoload-dev": {
        "psr-4": { "Tests\\": "tests/" }
    }
}
```

- **`psr-4`:** сопоставляет префикс пространства имён с директорией. `App\Service\Mailer` загружается из `src/Service/Mailer.php`.
- **`classmap`:** Composer сканирует директории и строит карту «класс — файл». Подходит для легаси-кода без пространств имён.
- **`files`:** подключаются при каждом запросе. PHP не умеет автозагружать функции, поэтому глобальные функции-хелперы попадают сюда. Держите этот список коротким.
- **`psr-0`:** устаревший предшественник PSR-4.

После изменения этих правил выполните `composer dump-autoload`.

## Оптимизация автозагрузчика

- **`--optimize-autoloader` (`-o`):** превращает правила PSR-4 и PSR-0 в карту классов. Классы, которых нет в карте, по-прежнему ищутся по правилам PSR-4.
- **`--classmap-authoritative` (`-a`):** включает `-o` и никогда не ищет на диске классы, которых нет в карте. Самый быстрый вариант, но классы, сгенерированные во время работы, не найдутся.
- **`--apcu-autoloader`:** кэширует поиск классов в APCu. Требует расширение APCu.

Типичная сборка для прода:

```bash
composer install --no-dev --optimize-autoloader --classmap-authoritative --no-interaction
```

## Нужно ли коммитить `composer.lock`

- **Приложение:** коммитьте всегда. Тогда разработчики, CI и прод устанавливают одни и те же версии.
- **Библиотека:** её lock-файл игнорируется, когда библиотеку устанавливают как зависимость. Коммит lock-файла делает окружение разработки в команде одинаковым, но может скрыть несовместимость с новыми версиями зависимостей. Тестируйте библиотеки в CI и с `composer update --prefer-lowest`, и с `composer update`.

Не разрешайте конфликты в `composer.lock` вручную. Возьмите одну из сторон и выполните `composer update vendor/package` для пакетов, изменённых в другой.

## Скрипты и плагины

```json
{
    "scripts": {
        "test": "phpunit",
        "analyse": "phpstan analyse"
    },
    "config": {
        "allow-plugins": {
            "symfony/flex": true
        }
    }
}
```

- **Скрипты** — команды в секции `scripts`. Их запускают по имени (`composer test`) или привязывают к событиям, например `post-install-cmd`, `post-update-cmd` и `post-autoload-dump`. `--no-scripts` их отключает.
- **Плагины** — пакеты с типом `composer-plugin`, которые расширяют Composer, например `symfony/flex` или `phpstan/extension-installer`. Плагин выполняет код во время `install`, поэтому начиная с Composer 2.2 каждый плагин нужно разрешить в `config.allow-plugins`.

## Платформенные требования

Пакеты могут требовать версию PHP и расширения, например `"php": "^8.2"` или `"ext-intl": "*"`. Composer проверяет их на том PHP, которым запущен, и генерирует `vendor/composer/platform_check.php`, который падает во время работы, если PHP на сервере слишком старый.

Если у разработчиков PHP 8.4, а на проде PHP 8.2, `composer update` может выбрать версии, которым нужен PHP 8.3. Укажите платформу прода:

```json
{
    "config": {
        "platform": {
            "php": "8.2.0"
        }
    }
}
```

`composer check-platform-reqs` проверяет сервер перед деплоем. Избегайте `--ignore-platform-reqs`: он скрывает реальную несовместимость.

## Разрешение конфликтов зависимостей

1. Прочитайте ошибку: Composer выводит цепочку конфликтующих ограничений.
2. `composer why vendor/package` показывает, какие пакеты требуют данный пакет. `composer why-not vendor/package 2.0` показывает, что блокирует версию.
3. Обновляйте связанные пакеты вместе: `-w` (`--with-dependencies`) обновляет и их зависимости, а `-W` (`--with-all-dependencies`) — ещё и зависимости, указанные в корневом `require`.
4. Ослабьте свои ограничения либо обновите или замените пакет, который блокирует обновление.
5. Как временную меру используйте форк в `repositories` или inline-алиас вида `"vendor/package": "dev-fix as 1.4.0"`.

## `provide`, `replace` и `conflict`

- **`provide`:** пакет реализует виртуальный пакет. `monolog/monolog` предоставляет `psr/log-implementation`, поэтому библиотека может требовать этот виртуальный пакет и оставить выбор логгера приложению.
- **`replace`:** пакет содержит код другого пакета, и Composer не устанавливает этот другой пакет. Проекты на свежем PHP иногда заменяют ненужные полифилы: `"replace": {"symfony/polyfill-php80": "*"}`.
- **`conflict`:** версии, которые нельзя установить вместе с пакетом, например `"conflict": {"doctrine/orm": "<2.15"}`.

## Безопасность зависимостей

- `composer audit` проверяет установленные пакеты по базе уязвимостей. Composer также запускает его после `require` и `update`. Добавьте его в CI.
- `roave/security-advisories` конфликтует со всеми известными уязвимыми версиями, поэтому Composer откажется их устанавливать.
- Коммитьте `composer.lock` и используйте `composer install` в CI и на проде.
- Разрешайте в `config.allow-plugins` только доверенные плагины.
- Dependabot или Renovate открывают пул-реквесты с новыми версиями, и тесты проверяют каждое обновление.
- Каждый пакет и его зависимости — это чужой код в проекте. Перед добавлением пакета проверьте, поддерживается ли он.

## Приватные пакеты и монорепозитории

```json
{
    "repositories": [
        { "type": "vcs", "url": "git@github.com:acme/billing-sdk.git" },
        { "type": "path", "url": "packages/*", "options": { "symlink": true } }
    ],
    "require": {
        "acme/billing-sdk": "^2.1",
        "acme/shared-kernel": "*@dev"
    }
}
```

- **`vcs`:** Git-репозиторий. Composer читает его теги и ветки как версии. При большом числе пакетов работает медленно.
- **`composer`:** реестр пакетов: Satis (self-hosted), Private Packagist или реестры пакетов GitLab и GitHub.
- **`path`:** локальная директория, подключённая в `vendor/` симлинком. Подходит для монорепозиториев и разработки пакета вместе с приложением.

Храните учётные данные в `auth.json`, добавленном в `.gitignore`, или в переменной окружения `COMPOSER_AUTH` в CI.

## PHP-CS-Fixer

[PHP-CS-Fixer](https://github.com/PHP-CS-Fixer/PHP-CS-Fixer) исправляет стиль кода по наборам правил вроде `@PER-CS` или `@Symfony`: форматирование, отступы, порядок импортов и подобное. Запускайте `php-cs-fixer fix --dry-run --diff` в CI, чтобы сообщать о нарушениях, и `php-cs-fixer fix` локально или в pre-commit хуке. Laravel Pint — преднастроенная обёртка над PHP-CS-Fixer. Альтернатива — PHP_CodeSniffer: `phpcs` сообщает о нарушениях, а `phpcbf` исправляет их.

## Rector

[Rector](https://getrector.com/) автоматически меняет код по включённым правилам. Типичные задачи: переход на новый синтаксис PHP, например constructor property promotion или `match`, обновление Symfony, Laravel или PHPUnit, добавление объявлений типов и удаление мёртвого кода. `rector process --dry-run` показывает изменения, не применяя их. Проверяйте результат и прогоняйте тесты: Rector переписывает код массово.

## Профилирование

Сначала измеряйте, потом оптимизируйте:

- **APM** (New Relic, Datadog, инструменты на основе OpenTelemetry) записывает каждый запрос и показывает, какие эндпоинты, запросы к БД и внешние вызовы медленные.
- **Профайлеры** показывают, на что тратит время отдельный запрос. Blackfire — коммерческий профайлер, который может безопасно профилировать выбранные запросы на проде. XHProf и SPX — open-source альтернативы. Tideways объединяет APM и профайлер.

Типичные находки в PHP-приложениях: N+1 запросы к БД, отсутствующие индексы, отсутствие кэша и неоптимизированный автозагрузчик.

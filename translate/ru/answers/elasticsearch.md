# Концепции Elasticsearch

## Основные возможности
- **Распределённость и работа в реальном времени**: данные индексируются и становятся доступными для поиска практически мгновенно в кластере узлов.
- **RESTful API**: взаимодействие с данными через стандартные HTTP-методы и JSON.
- **Полнотекстовый поиск**: работает на базе Apache Lucene, поддерживает сложные текстовые запросы (нечёткий поиск, подсветка, стемминг).
- **Документо-ориентированность**: данные хранятся в виде JSON-документов, что делает хранилище бессхемным (хотя схемы можно задать явно).
- **Инвертированный индекс**: вместо хранения строк создаётся индекс терминов с указанием документов, в которых они содержатся, что обеспечивает чрезвычайно быстрый поиск.
- **Масштабируемость**: шардирование и репликация позволяют обрабатывать огромные объёмы данных и обеспечивать высокую доступность.

---

## Анализаторы
Анализаторы используются при индексации и поиске для обработки текста. Анализатор состоит из:
1. **Character Filters**: модифицируют текст перед токенизацией (например, удаляют HTML-теги).
2. **Tokenizer**: разбивает текст на токены (обычно слова).
3. **Token Filters**: модифицируют токены (например, приведение к нижнему регистру, удаление стоп-слов вроде «the» или «and», стемминг).

### Standard Analyzer
Анализатор по умолчанию, который хорошо работает для большинства языков. Разбивает текст по границам слов и удаляет пунктуацию.

### Пользовательские анализаторы
Вы можете определить собственные анализаторы для обработки специфических случаев — например, индексации адресов электронной почты или идентификаторов продуктов.

## Основные понятия
- **Кластер**: группа узлов с общими данными, которая идентифицируется по имени.
- **Узел**: один сервер Elasticsearch. У узлов есть роли: master-eligible, data, ingest, coordinating и другие.
- **Индекс**: набор JSON-документов с общим маппингом, например `products` или `logs-2026.11.15`.
- **Документ**: JSON-объект в индексе, который идентифицируется по `_id`.
- **Маппинг**: имена и типы полей индекса и то, как анализируется каждое поле.
- **Шард**: индекс делится на первичные шарды, и каждый из них — отдельный индекс Lucene. Шарды распределяются по узлам, поэтому индекс может вырасти за пределы одного сервера.
- **Реплика**: копия первичного шарда на другом узле. Реплики защищают от отказа узла и тоже обслуживают поиск.

Типы маппинга удалены в Elasticsearch 8.0, поэтому старая аналогия «индекс = база данных, тип = таблица» больше не работает.

## Когда использовать Elasticsearch
Elasticsearch подходит для полнотекстового поиска с ранжированием по релевантности, устойчивостью к опечаткам и синонимами, для фильтрации каталога со счётчиками фасетов, анализа логов и метрик (Elastic Stack) и агрегаций по большим объёмам данных.

Основным источником истины он быть не должен:
- В нём нет транзакций по нескольким документам и JOIN, кроме ограниченных типов полей `nested` и `join`.
- Новый документ находится поиском только после refresh.
- Смена типа поля требует полной переиндексации.
- В нём нет ограничений целостности и внешних ключей.

Обычно данные хранят в MySQL или PostgreSQL, а Elasticsearch служит поисковым индексом, который синхронизируется с БД и может быть пересоздан в любой момент.

## `text` и `keyword`
- **`text`**: значение разбивается анализатором на токены, например приводится к нижнему регистру и стеммингуется. Используйте его для полнотекстового поиска по заголовкам и описаниям. Для сортировки и агрегаций он эффективно не подходит.
- **`keyword`**: значение хранится как один точный токен. Используйте его для фильтров, сортировки и агрегаций по статусам, тегам, email и ID.

Без явного маппинга строка индексируется как поле `text` с подполем `.keyword`. Явный маппинг избавляет от сюрпризов:

```json
{
    "mappings": {
        "properties": {
            "title": { "type": "text", "fields": { "raw": { "type": "keyword" } } },
            "status": { "type": "keyword" },
            "price": { "type": "scaled_float", "scaling_factor": 100 }
        }
    }
}
```

## `match` и `term`
- **`match`** пропускает строку поиска через анализатор поля и ищет получившиеся токены. Запрос `match` по `title` со строкой «Red Shoes» найдёт документы с «red» или «shoes». Чтобы требовать оба слова, добавьте `"operator": "and"`.
- **`term`** ищет точное значение без анализа. Используйте его для полей `keyword`, числовых полей, дат и булевых значений.

Запрос `term` со строкой «Red Shoes» по полю `text` ничего не найдёт: в индексе лежат токены «red» и «shoes», а не исходная строка.

## Query context, filter context и `bool`
- **Query context** вычисляет, насколько хорошо документ подходит, и задаёт его `_score`.
- **Filter context** только проверяет, подходит ли документ. Оценка не вычисляется, а часто используемые фильтры Elasticsearch кэширует.

Запрос `bool` объединяет условия:
- `must`: должно выполняться и влияет на оценку.
- `should`: повышает оценку, если выполняется. Если нет `must` или `filter`, должно выполниться хотя бы одно условие `should`.
- `filter`: должно выполняться, без вычисления оценки.
- `must_not`: не должно выполняться.

```json
{
    "query": {
        "bool": {
            "must": [{ "match": { "title": "running shoes" } }],
            "filter": [
                { "term": { "status": "active" } },
                { "range": { "price": { "gte": 50, "lte": 150 } } }
            ],
            "must_not": [{ "term": { "brand": "noname" } }]
        }
    }
}
```

## Оценка релевантности
По умолчанию Elasticsearch использует BM25. Оценка документа зависит от:
- **Частоты термина**: чем чаще термин встречается в поле, тем выше оценка, но рост замедляется.
- **Обратной частоты документа**: термин, редкий в индексе, весит больше, чем частый.
- **Длины поля**: совпадение в коротком поле, например в заголовке, весит больше, чем в длинном тексте.

Повышайте вес полей через `"title^3"` в запросе `multi_match` или корректируйте оценку по популярности, свежести или расстоянию через `function_score`. `"explain": true` показывает, как вычислена оценка. Частоты документов считаются по каждому шарду отдельно, поэтому в маленьких индексах оценки могут выглядеть непоследовательно.

## Глубокая пагинация
- **`from` и `size`**: каждый шард возвращает координирующему узлу `from + size` документов, поэтому дальние страницы дорогие. По умолчанию `from + size` не может превышать 10 000 (`index.max_result_window`).
- **`search_after` с point in time (PIT)**: передавайте значения сортировки последнего документа предыдущей страницы. Каждая страница стоит одинаково, а PIT сохраняет согласованное состояние индекса между запросами. Перейти на произвольный номер страницы нельзя.
- **`scroll`**: старый API для выгрузки больших результатов. Сейчас Elastic рекомендует вместо него `search_after` с PIT.

Сильное увеличение `max_result_window` может исчерпать память heap.

## Агрегации
Агрегации вычисляют статистику по документам, найденным запросом, в том же запросе, что и поиск:
- **Метрические агрегации**: `avg`, `sum`, `min`, `max`, `stats`, `cardinality` (приблизительное число уникальных значений) и `percentiles`.
- **Bucket-агрегации**: `terms`, `range`, `histogram` и `date_histogram` группируют документы по корзинам.
- **Pipeline-агрегации**: работают с результатами других агрегаций, например `derivative` или `bucket_sort`.

Агрегации можно вкладывать друг в друга, например средняя цена по категориям по месяцам. Фасеты интернет-магазина вида «Бренд: Nike (120)» — это агрегации `terms`. Агрегируйте по полям `keyword`, числовым полям и датам.

## Пакетная индексация из PHP
В примере используется официальный клиент `elasticsearch/elasticsearch` 8.x, установленный через Composer, без фреймворка. `$products` — массив строк, загруженных из БД.

```php
use Elastic\Elasticsearch\ClientBuilder;

$client = ClientBuilder::create()->setHosts(['http://localhost:9200'])->build();

foreach (array_chunk($products, 1000) as $chunk) {
    $body = [];
    foreach ($chunk as $product) {
        $body[] = ['index' => ['_index' => 'products', '_id' => $product['id']]];
        $body[] = ['title' => $product['title'], 'price' => $product['price']];
    }

    $response = $client->bulk(['body' => $body])->asArray();
    if ($response['errors']) {
        // Часть операций не выполнилась: проверьте $response['items'] и повторите или залогируйте их.
    }
}
```

- Держите размер bulk-запроса в пределах нескольких мегабайт и подбирайте его замерами.
- `_bulk` возвращает HTTP 200, даже если часть операций не выполнилась, поэтому всегда проверяйте `errors`.
- При большом первичном импорте установите `refresh_interval` в `-1` и `number_of_replicas` в `0`, а после импорта верните оба значения.

## Состояние кластера
`GET _cluster/health` возвращает один из трёх статусов:
- **Green**: все первичные шарды и реплики размещены.
- **Yellow**: все первичные шарды размещены, но часть реплик — нет. Все данные доступны, но при отказе узла часть может потеряться. Кластер из одного узла с `number_of_replicas: 1` всегда жёлтый: реплику нельзя разместить на том же узле, что и первичный шард.
- **Red**: не размещён хотя бы один первичный шард, и часть данных недоступна.

`GET _cat/shards?v` и `GET _cluster/allocation/explain` показывают, почему шард не размещён. Частые причины — отказ узла, заполненный диск и невыполнимые правила размещения. Когда диск достигает порога flood stage (по умолчанию 95%), Elasticsearch переводит индексы на нём в режим только для чтения.

## Синхронизация с основной базой данных
- **Двойная запись**: приложение пишет в БД, а затем в Elasticsearch. Если вторая запись не удалась, данные расходятся.
- **Очередь**: после коммита в БД публикуется событие, например `ProductUpdated`, а воркер перечитывает запись и индексирует её. Паттерн Transactional Outbox гарантирует публикацию события: оно записывается в таблицу `outbox` в той же транзакции и публикуется позже.
- **Change data capture (CDC)**: инструмент вроде Debezium читает binlog или WAL базы и передаёт изменения в Kafka, а консьюмер индексирует их. Так ловятся и изменения в обход приложения, но появляется дополнительная инфраструктура.
- **Периодическая синхронизация**: задача по расписанию переиндексирует строки, изменённые после `updated_at`. Добавляет задержку и не замечает удалённые строки.

В любом случае используйте первичный ключ из БД как `_id`, чтобы индексация была идемпотентной, защищайтесь от обновлений не по порядку через внешнее версионирование или перечитывание актуального состояния и держите наготове процедуру полной переиндексации.

## Изменение маппинга без простоя
В маппинг можно добавлять новые поля, но нельзя менять тип существующего. Вместо этого переиндексируйте данные за алиасом:

1. Приложение обращается к алиасу, например `products`, а не к конкретному индексу вроде `products_v1`.
2. Создайте `products_v2` с новым маппингом.
3. Скопируйте данные через API `_reindex` или повторным импортом из БД.
4. Примените изменения, сделанные во время копирования, например записывая в оба индекса или переигрывая события.
5. Атомарно переключите алиас:

```json
POST _aliases
{
    "actions": [
        { "remove": { "index": "products_v1", "alias": "products" } },
        { "add": { "index": "products_v2", "alias": "products" } }
    ]
}
```

6. Удалите старый индекс, когда новый проверен. Для отката переключите алиас обратно.

`"dynamic": "strict"` отклоняет документы с неизвестными полями. Это защищает от неверно угаданных типов и маппинга с тысячами полей.

## Шарды и реплики
- **Первичные шарды** фиксируются при создании индекса. Чтобы изменить их число, нужна переиндексация или API `_split` и `_shrink`. По умолчанию шард один.
- **Реплики** можно менять в любой момент. Каждая добавляет отказоустойчивость и производительность поиска, но занимает место на диске и нагружает индексацию.

Рекомендации:
- Стремитесь к шардам размером примерно от 10 до 50 ГБ.
- Избегайте множества мелких шардов: каждый шард занимает память heap, а поиск выполняется на каждом шарде индекса.
- Для логов и других данных, привязанных ко времени, используйте data streams с Index Lifecycle Management (ILM). ILM переключается на новый индекс по размеру или возрасту и проводит старые индексы через фазы hot, warm, cold и delete.
- На проде используйте минимум три master-eligible узла и минимум одну реплику.

## Refresh, flush и translog
Поиск в Elasticsearch работает почти в реальном времени:

1. Новый документ попадает в буфер в памяти и в translog — журнал на диске, который обеспечивает его сохранность.
2. **Refresh**, по умолчанию раз в секунду (`refresh_interval`), записывает буфер в новый сегмент Lucene, видимый поиску. `GET` по `_id` находит документ и до refresh.
3. **Flush** фиксирует сегменты на диске и очищает translog.
4. В фоне мелкие сегменты сливаются в крупные, а удалённые документы вычищаются.

- Если пользователь должен сразу увидеть своё изменение, добавьте `?refresh=wait_for` к запросу на запись. `?refresh=true` под нагрузкой создаёт много мелких сегментов.
- При интенсивной индексации увеличьте `refresh_interval`, например до `30s`.
- Обновление помечает старый документ удалённым и записывает новый, поэтому часто обновляемые документы, например счётчики, обходятся дорого.

## Автодополнение и устойчивость к опечаткам
- **Нечёткий поиск**: `"fuzziness": "AUTO"` в запросе `match` допускает до двух правок в зависимости от длины слова, поэтому «iphnoe» находит «iphone».
- **Edge n-grams**: анализатор при индексации сохраняет префиксы слов («lap», «lapt», «lapto», «laptop»), и поиск по префиксу сводится к простому поиску термина. При поиске используйте стандартный анализатор.
- **`search_as_you_type`**: тип поля, который автоматически создаёт подполя для префиксов. Запрашивайте его через `multi_match` с типом `bool_prefix`.
- **Completion suggester**: поле `completion`, которое хранится в памяти. Самый быстрый вариант для подсказок в строке поиска, но поддерживает только поиск по префиксу.
- **Синонимы и языковые анализаторы**: фильтр синонимов («tv» и «television») и языковой анализатор, например `russian`, находят больше релевантных документов.

Поисковики часто комбинируют эти подходы: `search_as_you_type` для подсказок, `fuzziness` для основного поиска и повышение веса точных совпадений, чтобы они были выше нечётких.

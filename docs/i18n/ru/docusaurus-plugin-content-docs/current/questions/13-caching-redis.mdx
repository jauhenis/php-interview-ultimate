# 13. Кэширование и Redis

### Что такое кэширование?

<span className="badge badge--success margin-bottom--md">Junior</span>

**Ответ:** Сохранение данных во временном хранилище (например, в оперативной памяти) для более быстрого извлечения при последующих запросах.

---

### Что такое Redis и для чего его используют, кроме кэширования?

<span className="badge badge--success margin-bottom--md">Junior</span>

**Ответ:** Redis (REmote DIctionary Server) — это in-memory хранилище структур данных. Данные лежат в оперативной памяти, поэтому чтение и запись занимают доли миллисекунды. Типичные сценарии:

- **Кэш**: результаты запросов, отрендеренные фрагменты, ответы внешних API.
- **Хранилище сессий**: `session.save_handler = redis` с расширением phpredis, общее для всех серверов приложения.
- **Очереди**: очереди Laravel (списки + sorted sets), Redis-транспорт Symfony Messenger (streams).
- **Счётчики и rate limiting**: атомарная команда `INCR`.
- **Лидерборды и рейтинги**: sorted sets.
- **Распределённые блокировки**: `SET lock:key token NX PX 30000`.
- **Обмен сообщениями**: Pub/Sub и Streams.

---

### Какие типы данных поддерживает Redis?

<span className="badge badge--success margin-bottom--md">Junior</span>

**Ответ:**

- **String**: бинарно-безопасное значение до 512 МБ. Также используется как целочисленный счётчик (`INCR`, `INCRBY`) и как битовая карта (`SETBIT`, `BITCOUNT`).
- **Hash**: словарь «поле → значение», идеален для объектов (`HSET user:1 name John age 30`).
- **List**: упорядоченная последовательность с быстрыми вставкой и извлечением с обоих концов (`LPUSH`, `RPOP`, блокирующий `BLPOP`). Подходит для простых очередей.
- **Set**: неупорядоченное множество уникальных строк (`SADD`, `SISMEMBER`, `SINTER`). Подходит для тегов и подсчёта уникальных посетителей.
- **Sorted Set (ZSet)**: уникальные элементы, упорядоченные по числовому score (`ZADD`, `ZRANGE`, `ZRANK`). Подходит для лидербордов, отложенных задач и rate limiting со скользящим окном.
- **Stream**: append-only лог с группами консьюмеров (`XADD`, `XREADGROUP`).
- **Специальные типы**: HyperLogLog (приблизительный подсчёт уникальных элементов в ~12 КБ с погрешностью ~0,81%), геоиндексы (`GEOADD`, `GEOSEARCH`) и Bitfields.
- JSON, временные ряды и вероятностные структуры (Bloom filter и др.) раньше входили в Redis Stack, а начиная с Redis 8 встроены в ядро.

---

### Что такое TTL в Redis и как работает истечение ключей?

<span className="badge badge--success margin-bottom--md">Junior</span>

**Ответ:** TTL (Time To Live) — время жизни ключа. Задаётся через `SET key value EX 60`, `EXPIRE key 60`, `PEXPIRE` (в миллисекундах) или `EXPIREAT` (Unix timestamp). `TTL key` возвращает оставшиеся секунды: `-1` — у ключа нет срока жизни, `-2` — ключа не существует. `PERSIST` снимает ограничение. Важно: перезапись ключа обычным `SET` сбрасывает TTL (если не передать `KEEPTTL`).

Истёкшие ключи удаляются двумя способами:

- **Пассивно**: когда клиент обращается к истёкшему ключу, Redis удаляет его и ничего не возвращает.
- **Активно**: фоновый цикл регулярно берёт случайную выборку ключей с TTL и удаляет истёкшие.

Поэтому истёкший ключ может ещё какое-то время занимать память.

### Почему Redis такой быстрый?

<span className="badge badge--success margin-bottom--md">Junior</span>

**Ответ:**

- **Данные хранятся в RAM**, при чтении нет дискового I/O.
- **Команды выполняются в одном потоке**: нет блокировок и переключений контекста между командами, каждая команда атомарна.
- **Мультиплексирование I/O** (epoll/kqueue) позволяет одному потоку обслуживать тысячи соединений без блокировок.
- **Компактные специализированные кодировки** (listpack, intset, skiplist) экономят память и снижают промахи CPU-кэша.
- **Простой протокол** (RESP) дёшево парсить.

Начиная с Redis 6 сетевое чтение и запись можно вынести в отдельные I/O-потоки (`io-threads`), но команды по-прежнему выполняются строго по одной. Обратная сторона: одна медленная команда (`KEYS *`, `HGETALL` на огромном хеше, тяжёлый Lua-скрипт) блокирует всех остальных клиентов.

### Redis и Memcached: сравнение

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:**

- **Redis:** Поддерживает различные типы данных (строки, списки, множества и др.), персистентность и механизм pub/sub.
- **Memcached:** Простое хранилище «ключ-значение», в основном для простого кэширования.

### Какие стратегии кэширования вы знаете?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:**

- **Cache-Aside (Lazy Loading)**: приложение читает из кэша, при промахе загружает данные из БД и кладёт их в кэш. Самый распространённый паттерн в PHP (`Cache::remember()` в Laravel, `$cache->get($key, $callback)` в Symfony). Кэшируется только то, что реально запрашивают, но первый запрос медленный, а данные могут устаревать до истечения TTL.
- **Read-Through**: при промахе кэш-слой сам загружает данные из БД, приложение общается только с кэшем.
- **Write-Through**: каждая запись синхронно идёт и в кэш, и в БД. Кэш всегда актуален, но запись медленнее.
- **Write-Behind (Write-Back)**: запись идёт в кэш, а в БД сбрасывается асинхронно, часто пачками. Запись очень быстрая, но данные можно потерять, если кэш упадёт до сброса.
- **Refresh-Ahead**: горячие ключи обновляются в фоне до истечения срока жизни.

```php
function getUser(Redis $redis, PDO $pdo, int $id): ?array
{
    $key = "user:{$id}";

    $cached = $redis->get($key);
    if ($cached !== false) {
        return json_decode($cached, true);
    }

    $stmt = $pdo->prepare('SELECT * FROM users WHERE id = ?');
    $stmt->execute([$id]);
    $user = $stmt->fetch(PDO::FETCH_ASSOC) ?: null;

    if ($user !== null) {
        $redis->setex($key, 3600, json_encode($user));
    }

    return $user;
}
```

### Как инвалидировать кэш?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:** «В программировании есть только две сложные вещи: инвалидация кэша и придумывание имён» (Фил Карлтон). Основные подходы:

- **TTL**: самый простой вариант. Мы миримся с тем, что данные могут быть устаревшими до TTL секунд.
- **Явное удаление при записи**: после обновления БД ключ удаляют (`DEL`), а не обновляют. Удаление защищает от гонки, при которой два параллельных писателя оставляют в кэше более старое значение. Удалять нужно только после коммита транзакции в БД.
- **Версионированные ключи**: версия входит в ключ (`catalog:v42:product:1`). При повышении версии все старые ключи становятся недоступны и истекают по TTL.
- **Теги**: ключи группируются по тегам, и инвалидируется вся группа (`TagAwareCacheInterface::invalidateTags()` в Symfony, `Cache::tags()` в Laravel; драйверы file и database теги не поддерживают).
- **Инвалидация по событиям**: доменные события или CDC (например, Debezium) сбрасывают кэш в разных сервисах.

Даже у «удаления после коммита» есть пограничный случай: читатель может загрузить старое значение до коммита и записать его в кэш уже после удаления. Ущерб ограничивают коротким TTL или «отложенным двойным удалением» (delayed double delete).

### Что происходит, когда у Redis заканчивается память? Какие есть политики вытеснения?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:** Когда потребление памяти достигает `maxmemory`, Redis действует согласно `maxmemory-policy`:

- `noeviction` (по умолчанию): новые записи завершаются ошибкой OOM, чтение продолжает работать.
- `allkeys-lru` / `volatile-lru`: вытесняется давно не использовавшийся ключ среди всех ключей / среди ключей с TTL.
- `allkeys-lfu` / `volatile-lfu`: вытесняется реже всего используемый ключ (Redis 4.0+).
- `allkeys-random` / `volatile-random`: вытесняется случайный ключ.
- `volatile-ttl`: вытесняется ключ с наименьшим оставшимся TTL.

Для чистого кэша обычно выбирают `allkeys-lru` или `allkeys-lfu`. Если в том же инстансе лежат сессии, очереди или блокировки, вытеснение может незаметно их удалить. Тогда используйте политику `volatile-*` (и ставьте TTL только на кэш-ключи), а лучше отдельный инстанс. Если ни у одного ключа нет TTL, политики `volatile-*` ведут себя как `noeviction`. LRU и LFU приблизительные: Redis берёт выборку из нескольких ключей (`maxmemory-samples`, по умолчанию 5), а не хранит глобальный порядок.

### Как работает персистентность в Redis: RDB vs AOF?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:**

- **RDB (снапшоты)**: Redis периодически сохраняет снимок всего датасета на момент времени (правила `save`, `BGSAVE`). Для этого он форкает дочерний процесс, который пишет файл, используя механизм copy-on-write ОС. Файлы компактные, перезапуск быстрый, удобно для бэкапов. Но теряются все записи с момента последнего снапшота, а форк большого датасета может давать всплески латентности и дополнительный расход памяти.
- **AOF (Append Only File)**: каждая команда записи дописывается в лог. Надёжность задаёт `appendfsync`: `always` (надёжнее всего, но медленно), `everysec` (по умолчанию, теряется не больше ~1 секунды записей) или `no` (сброс на диск решает ОС). Лог сжимается в фоне через AOF rewrite. Файлы больше, перезапуск медленнее.
- **Гибридный режим** (`aof-use-rdb-preamble yes`, по умолчанию с Redis 5): переписанный AOF начинается с RDB-снапшота, за которым идут последние команды. Сочетает быстрый перезапуск и хорошую надёжность.
- **Без персистентности**: нормальный вариант для чистого кэша, который можно восстановить из БД.

Даже с AOF `always` репликация асинхронная, поэтому Redis не должен быть единственным местом хранения критичных данных.

### Почему нельзя использовать `KEYS *` на проде?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:** `KEYS` проходит по всему пространству ключей за O(N), а поскольку команды выполняются в одном потоке, сервер блокируется на всё время сканирования. При миллионах ключей это секунды. Вместо него используйте курсорный `SCAN` (`SCAN 0 MATCH user:* COUNT 100`): он возвращает небольшие порции и надолго не блокирует. Один и тот же ключ может вернуться несколько раз, а ключи, добавленные или удалённые во время итерации, могут как попасть в выдачу, так и нет. Для коллекций есть аналоги `HSCAN`, `SSCAN` и `ZSCAN`.

```php
$redis->setOption(Redis::OPT_SCAN, Redis::SCAN_RETRY);

$iterator = null;
while ($keys = $redis->scan($iterator, 'session:*', 1000)) {
    $redis->unlink($keys);
}
```

Другие команды, способные заблокировать Redis:

- `DEL` огромного ключа: используйте `UNLINK`, который освобождает память в фоновом потоке.
- `FLUSHALL` / `FLUSHDB`: используйте опцию `ASYNC`.
- `HGETALL`, `SMEMBERS`, `LRANGE 0 -1` на больших коллекциях.

Большие ключи ищут через `redis-cli --bigkeys`, медленные команды — через `SLOWLOG GET`. Опасные команды можно запретить пользователям приложения через ACL.

### Чем отличается pipelining от транзакций (MULTI/EXEC)?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:**

- **Pipelining**: клиент отправляет много команд, не дожидаясь ответа на каждую, а затем читает все ответы разом. Это экономит сетевые round trip'ы (1000 `GET` за один round trip вместо 1000). Pipelining **не атомарен**: между командами могут выполниться команды других клиентов.
- **MULTI/EXEC**: команды ставятся в очередь и выполняются единым изолированным блоком, команды других клиентов посередине не выполняются. **Отката нет**: если команда падает во время выполнения (например, `INCR` над нечисловой строкой), остальные команды всё равно применяются. Всю транзакцию отменяют (`EXECABORT`) только ошибки, обнаруженные при постановке в очередь (например, неверное число аргументов).
- **WATCH**: оптимистичная блокировка. Если отслеживаемый ключ изменился до `EXEC`, транзакция отменяется (`EXEC` возвращает null), и клиент повторяет попытку.
- Для атомарной логики «прочитать, решить, записать» используйте **Lua-скрипты** (`EVAL`): они выполняются на сервере атомарно.

```php
// Pipelining: один сетевой round trip
$pipe = $redis->pipeline();
foreach ($ids as $id) {
    $pipe->get("user:{$id}");
}
$users = $pipe->exec();

// Транзакция: обе команды выполняются вместе
$redis->multi()
    ->incr("views:{$pageId}")
    ->expire("views:{$pageId}", 86400)
    ->exec();
```

### phpredis vs Predis: какой PHP-клиент выбрать?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:**

- **phpredis**: расширение на C (`pecl install redis`). Быстрее и потребляет меньше памяти. Поддерживает persistent-соединения (`pconnect`), встроенные сериализаторы (igbinary, msgpack) и сжатие (lzf, zstd, lz4), Redis Cluster/Sentinel и нативный обработчик сессий. Требует установки расширения на каждом сервере и в каждом Docker-образе.
- **Predis**: библиотека на чистом PHP, ставится через Composer. Не требует расширений и легко расширяется, но медленнее, потому что протокол парсится на PHP.

Оба клиента поддерживаются Laravel (`REDIS_CLIENT`, по умолчанию `phpredis`) и компонентом Symfony Cache. Для прода обычно выбирают phpredis. Predis удобен, когда ставить расширения нельзя.

### Что такое cache stampede (dogpile effect) и как его предотвратить?

<span className="badge badge--warning margin-bottom--md">Senior</span>

**Ответ:** Когда истекает горячий ключ, множество параллельных запросов одновременно получают промах, и все они выполняют один и тот же тяжёлый запрос, чтобы пересчитать значение. Нагрузка на БД резко растёт, вплоть до каскадного отказа. Способы защиты:

- **Блокировка (mutex)**: пересчитывает значение только один процесс (`SET lock:key token NX EX 10`), остальные недолго ждут или отдают устаревшее значение. В Laravel есть `Cache::lock()`. В Symfony Cache метод `get()` блокирует автоматически, чтобы отсутствующее значение на сервере вычислял только один процесс.
- **Вероятностное раннее истечение (XFetch)**: каждый запрос может решить пересчитать значение до истечения TTL, причём вероятность растёт по мере приближения к истечению: `time() - $delta * $beta * log(random) >= $expiry`, где `$delta` — время пересчёта. Symfony Cache поддерживает это через аргумент `$beta` метода `get()`.
- **Stale-while-revalidate**: отдаём устаревшее значение, пока кэш обновляется в фоне. В Laravel: `Cache::flexible('stats', [300, 600], fn () => ...)`.
- **Фоновое обновление (прогрев кэша)**: cron или воркер очереди обновляет горячие ключи до их истечения, и пользователи никогда не видят промаха.
- **TTL jitter**: к TTL добавляется случайное смещение, чтобы много ключей не истекали одновременно.

### Что такое cache penetration, cache breakdown и cache avalanche и как с ними бороться?

<span className="badge badge--warning margin-bottom--md">Senior</span>

**Ответ:**

- **Cache penetration (пробой кэша)**: запросы к несуществующим данным (например, `id=-1` или случайные ID от бота). Таких данных никогда нет в кэше, поэтому каждый запрос идёт в БД. Решения: кэшировать результат «не найдено» с коротким TTL, поставить перед БД Bloom filter существующих ID (`BF.ADD` / `BF.EXISTS`), валидировать входные данные и ограничивать частоту запросов.
- **Cache breakdown**: истекает один очень горячий ключ, что приводит к stampede (см. предыдущий вопрос). Решения: блокировка, раннее обновление и stale-while-revalidate.
- **Cache avalanche (лавина)**: большая часть кэша пропадает разом, потому что много ключей записали с одинаковым TTL (например, при деплое или прогреве) или нода Redis перезапустилась с пустой памятью. Решения: TTL jitter (`3600 + random_int(0, 300)`), высокая доступность (реплики, Sentinel или Cluster), персистентность для «тёплого» перезапуска, постепенный прогрев кэша, circuit breaker или rate limiter перед БД и локальный in-process кэш (APCu) как второй уровень.

### Redis Sentinel vs Redis Cluster: в чём разница?

<span className="badge badge--warning margin-bottom--md">Senior</span>

**Ответ:** Оба решения построены на **репликации**: мастер и одна или несколько реплик. Репликация асинхронная, поэтому запись, подтверждённая мастером, может потеряться, если мастер упадёт до её передачи репликам. `WAIT numreplicas timeout` снижает этот риск, но не устраняет его.

- **Sentinel** обеспечивает высокую доступность для одной группы «мастер + реплики». Процессы Sentinel следят за мастером, договариваются о его отказе (кворум), повышают реплику до мастера и сообщают клиентам новый адрес. **Шардирования нет**: весь датасет должен помещаться в один мастер, а запись масштабируется только вертикально.
- **Cluster** обеспечивает **шардирование и высокую доступность**. Пространство ключей делится на 16384 hash-слота (`CRC16(key) mod 16384`), которые распределяются между несколькими мастерами, у каждого свои реплики, failover встроен. Ограничения:
  - Мультиключевые команды, транзакции и Lua-скрипты работают, только если все ключи в одном слоте. Используйте **hash tags**: в `{user:42}:profile` и `{user:42}:cart` хешируется только часть в фигурных скобках, поэтому оба ключа попадают в один слот.
  - Доступна только база 0 (нет `SELECT`).
  - Клиенты должны поддерживать кластер и обрабатывать редиректы `MOVED`/`ASK` (класс `RedisCluster` в phpredis или опция `cluster` в Predis).

Sentinel выбирают, когда данные помещаются на одну ноду и нужен автоматический failover. Cluster — когда нужно горизонтально масштабировать память или пропускную способность записи.

### Как реализовать rate limiter на Redis?

<span className="badge badge--warning margin-bottom--md">Senior</span>

**Ответ:** Распространённые алгоритмы:

- **Fixed window (фиксированное окно)**: `INCR` ключа вида `rate:{userId}:{minute}` и `EXPIRE` при первом обращении. Просто, но на границе окон допускает всплеск до 2× от лимита.
- **Sliding window log (журнал скользящего окна)**: sorted set, где score — время запроса. Старые записи удаляются (`ZREMRANGEBYSCORE`), оставшиеся считаются (`ZCARD`), новая добавляется (`ZADD`). Точно, но память растёт с числом запросов.
- **Sliding window counter / token bucket**: плавное ограничение с постоянным расходом памяти, обычно реализуется на Lua.

Проверка и инкремент должны быть атомарными. Если `INCR` и `EXPIRE` отправляются отдельно и процесс упадёт между ними, ключ будет жить вечно, и пользователь окажется заблокирован навсегда. Lua-скрипт выполняется атомарно:

```php
$script = <<<'LUA'
local current = redis.call('INCR', KEYS[1])
if current == 1 then
    redis.call('EXPIRE', KEYS[1], ARGV[1])
end
return current
LUA;

$key = sprintf('rate:%d:%d', $userId, intdiv(time(), 60));
$count = $redis->eval($script, [$key, 60], 1);

if ($count > 100) {
    http_response_code(429); // Too Many Requests
    exit;
}
```

Пока Lua-скрипт выполняется, Redis заблокирован, поэтому скрипты должны быть короткими. Загрузите скрипт один раз через `SCRIPT LOAD` и вызывайте его по хешу через `EVALSHA`, чтобы не передавать тело каждый раз. Во фреймворках используйте готовые решения: `RateLimiter` в Laravel или компонент RateLimiter в Symfony (fixed window, sliding window, token bucket). Оба умеют хранить состояние в Redis.

### Redis Pub/Sub vs Redis Streams: что и когда использовать?

<span className="badge badge--warning margin-bottom--md">Senior</span>

**Ответ:**

- **Pub/Sub** работает по принципу fire-and-forget: `PUBLISH channel message` доставляется только тем подписчикам, которые подключены в этот момент. Нет ни персистентности, ни подтверждений. Если подписчик офлайн или слишком медленный (лимит выходного буфера), сообщение теряется (доставка at-most-once). Подходит для real-time уведомлений, инвалидации кэша на нескольких серверах и рассылки через WebSocket (например, Laravel Broadcasting с драйвером Redis).
- **Streams** — персистентный append-only лог. Записи добавляются через `XADD` и имеют ID, историю можно читать (`XRANGE`). Группы консьюмеров (`XREADGROUP`) распределяют сообщения между воркерами, каждое сообщение нужно подтвердить через `XACK`, неподтверждённые остаются в Pending Entries List (`XPENDING`), а зависшие можно переназначить другому консьюмеру (`XAUTOCLAIM`). Это даёт доставку at-least-once, поэтому консьюмеры должны быть идемпотентными. Размер стрима ограничивают через `MAXLEN` или `MINID`. Redis-транспорт Symfony Messenger построен на Streams.

По сравнению с Kafka, Streams легче, но ограничены объёмом RAM и менее надёжны (асинхронная репликация). Kafka лучше подходит для больших объёмов, долгого хранения и повторного проигрывания событий. В PHP `subscribe()` и блокирующие вызовы `XREADGROUP` должны работать в долгоживущем CLI-воркере, а не в запросе PHP-FPM.

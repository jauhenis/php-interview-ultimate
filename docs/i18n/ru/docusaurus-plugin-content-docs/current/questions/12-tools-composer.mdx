# 12. Инструменты и Composer

### Что такое Composer?

<span className="badge badge--success margin-bottom--md">Junior</span>

**Ответ:** Менеджер зависимостей для PHP, позволяющий объявлять библиотеки, от которых зависит ваш проект, и управлять ими (устанавливать/обновлять).

---

### В чём разница между `composer.json` и `composer.lock`?

<span className="badge badge--success margin-bottom--md">Junior</span>

**Ответ:**

- `composer.json`: Содержит список необходимых зависимостей и ограничения по версиям.
- `composer.lock`: Хранит точные версии установленных пакетов.

---

### В чём разница между `composer install` и `composer update`?

<span className="badge badge--success margin-bottom--md">Junior</span>

**Ответ:**

- `composer install`: Проверяет наличие файла `composer.lock`. Если он существует, устанавливает точные версии, указанные в нём. Если нет — читает `composer.json`, устанавливает последние совместимые версии и создаёт lock-файл.
- `composer update`: Игнорирует `composer.lock` и пытается обновить все пакеты до последних версий, допустимых ограничениями в `composer.json`, после чего обновляет lock-файл.

---

### Что такое семантическое версионирование и что означают `^` и `~` в Composer?

<span className="badge badge--success margin-bottom--md">Junior</span>

**Ответ:** Семантическое версионирование (SemVer) использует формат `MAJOR.MINOR.PATCH`: **MAJOR** — изменения, ломающие обратную совместимость, **MINOR** — новая функциональность с сохранением совместимости, **PATCH** — обратно совместимые исправления багов. Ограничения версий в Composer:

- `1.2.3`: строго эта версия.
- `^1.2.3` (caret, рекомендуется): `>=1.2.3 <2.0.0`, то есть любая версия без ломающих изменений. Для версий `0.x` правило строже: `^0.3` означает `>=0.3.0 <0.4.0`, потому что в `0.x` любая минорная версия может ломать совместимость.
- `~1.2` (tilde): `>=1.2 <2.0`, а `~1.2.3` означает `>=1.2.3 <1.3.0`. Расти может только последний указанный сегмент.
- `>=1.0 <2.0`, `1.0 - 2.0`, `1.*` и `^1.0 || ^2.0`: диапазоны, wildcard и альтернативы.

### Чем отличается `require` от `require-dev`?

<span className="badge badge--success margin-bottom--md">Junior</span>

**Ответ:**

- `require`: пакеты, необходимые приложению для работы на проде (фреймворки, HTTP-клиенты, ORM).
- `require-dev`: пакеты, нужные только для разработки и CI (PHPUnit, PHPStan, PHP-CS-Fixer, Faker, debug-панели). Устанавливаются через `composer require --dev vendor/package`.

На проде запускают `composer install --no-dev`, чтобы dev-пакеты не ставились. Так `vendor` становится меньше, а поверхность атаки — уже. `autoload-dev` (например, пространство имён `Tests\`) при `--no-dev` тоже пропускается. Dev-зависимости сторонних пакетов не устанавливаются никогда, только ваши собственные (корневые) `require-dev`.

### Что такое директория `vendor` и нужно ли коммитить её в Git?

<span className="badge badge--success margin-bottom--md">Junior</span>

**Ответ:** `vendor/` — директория, куда Composer устанавливает зависимости и генерирует автозагрузчик (`vendor/autoload.php`). Коммитить её **не нужно**: добавьте её в `.gitignore`. Зависимости полностью описаны в `composer.json` + `composer.lock`, и любой может воссоздать `vendor/` командой `composer install`. Коммит раздувает репозиторий и порождает огромные нечитаемые диффы и конфликты при мерже. Никогда не правьте файлы в `vendor/` напрямую: изменения пропадут при следующей установке. Чтобы исправить баг в зависимости, отправьте патч в апстрим, используйте форк или примените патч плагином вроде `cweagans/composer-patches`.

### Чем отличается `git fetch` от `git pull`?

<span className="badge badge--success margin-bottom--md">Junior</span>

**Ответ:**

- `git fetch` скачивает новые коммиты с удалённого репозитория и обновляет remote-tracking ветки (например, `origin/main`), но не трогает вашу рабочую ветку. Это всегда безопасно.
- `git pull` — это `git fetch`, за которым следует `git merge` удалённой ветки в текущую (или `git rebase` при `git pull --rebase` либо `pull.rebase = true`).

Используйте `fetch`, когда хотите посмотреть изменения перед интеграцией (`git log main..origin/main`).
[Git: Merge vs Rebase vs Pull vs Fetch](../answers/git.md)

### Что такое автозагрузка (Autoloading) и как Composer с ней работает?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:** Автозагрузка автоматически подключает файлы классов, когда они необходимы. Composer использует PSR-4 (и другие стандарты) для сопоставления пространств имён с директориями.

---

### Какие типы автозагрузки поддерживает Composer?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:**

- **`psr-4`** (рекомендуется): сопоставляет префикс пространства имён с директорией (`"App\\": "src/"`, и `App\Service\Mailer` загружается из `src/Service/Mailer.php`).
- **`psr-0`**: устаревший предшественник PSR-4, где полное пространство имён отражается в пути, а подчёркивания в именах классов превращаются в разделители директорий.
- **`classmap`**: Composer сканирует указанные директории и строит карту `класс → файл`. Полезно для легаси-кода без пространств имён.
- **`files`**: файлы, которые подключаются при **каждом** запросе (например, глобальные функции-хелперы). Функции нельзя загрузить автозагрузчиком, но этот список стоит держать коротким.

`autoload-dev` имеет ту же структуру и используется для тестовых классов. После изменения правил автозагрузки выполните `composer dump-autoload`, чтобы перегенерировать автозагрузчик.

---

### Как оптимизировать автозагрузчик Composer для прода?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:**

- **Уровень 1, `--optimize` / `-o`**: превращает правила PSR-4/PSR-0 в classmap, и большинство классов находится одним поиском по массиву, без проверок файловой системы. Если класса нет в карте, Composer всё равно откатывается к правилам PSR-4.
- **Уровень 2/A, `--classmap-authoritative` / `-a`**: включает `-o` и заставляет автозагрузчик доверять только classmap. Неизвестные классы на диске не ищутся. Это самый быстрый вариант, но классы, сгенерированные в рантайме (например, прокси), не будут найдены.
- **Уровень 2/B, `--apcu-autoloader`**: кэширует результаты поиска классов (включая промахи) в APCu. Требует расширение APCu.

Типичная сборка для прода:

```bash
composer install --no-dev --optimize-autoloader --classmap-authoritative --no-interaction
```

С OPcache preloading можно пойти дальше и загружать самые используемые классы в общую память при старте сервера.

### Нужно ли коммитить `composer.lock`? Есть ли разница между приложением и библиотекой?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:**

- **Приложение**: `composer.lock` коммитят всегда. Все разработчики, CI и прод получают одни и те же версии зависимостей, проблемы «у меня работает» исчезают, а деплой становится воспроизводимым.
- **Библиотека**: lock-файл библиотеки **игнорируется**, когда она устанавливается как зависимость, — важны только ограничения в её `composer.json`. Коммитить его необязательно: он делает dev-окружение команды единообразным, но может скрывать несовместимости с новыми версиями зависимостей. Библиотеки стоит тестировать в CI и на самых низких, и на самых высоких допустимых версиях (`composer update --prefer-lowest` и обычный `composer update`).

Конфликты в `composer.lock` не правят руками: берут одну из сторон и заново выполняют `composer update <package>` (или `composer update --lock`) для изменённых пакетов.

### Что такое скрипты и плагины Composer?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:**

- **Скрипты** — команды из секции `scripts` в `composer.json`. Это могут быть собственные алиасы (`"test": "phpunit"`, запуск через `composer test`) или хуки на события Composer (`post-install-cmd`, `post-update-cmd`, `post-autoload-dump`), например для очистки кэша или публикации ассетов. Отключаются флагом `--no-scripts`.
- **Плагины** — пакеты Composer (тип `composer-plugin`), которые встраиваются во внутренности Composer: например, `symfony/flex` (рецепты), `phpstan/extension-installer` и `cweagans/composer-patches`. Начиная с Composer 2.2 плагины нужно явно разрешать в `config.allow-plugins`, потому что плагин выполняет произвольный код во время `install`.

```json
{
  "scripts": {
    "test": "phpunit",
    "analyse": "phpstan analyse",
    "post-autoload-dump": ["@php artisan package:discover --ansi"]
  },
  "config": {
    "allow-plugins": {
      "symfony/flex": true
    }
  }
}
```

### Что такое платформенные требования и зачем нужен `config.platform`?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:** Пакеты могут требовать версию PHP и расширения: `"php": "^8.2"`, `"ext-redis": "*"`, `"ext-intl": "*"`. Composer сверяет их с PHP, на котором запущен сам Composer, а начиная с Composer 2 ещё и генерирует `vendor/composer/platform_check.php`, который падает в рантайме, если PHP на сервере слишком старый.

Проблема: у разработчика локально PHP 8.4, а на проде PHP 8.2. `composer update` может выбрать версии пакетов, требующие PHP 8.3+, и прод сломается. Решение — зафиксировать целевую платформу в `composer.json`:

```json
{
  "config": {
    "platform": {
      "php": "8.2.0"
    }
  }
}
```

Тогда Composer разрешает зависимости так, будто работает на PHP 8.2. В пайплайне деплоя используйте `composer check-platform-reqs`, чтобы проверить, что сервер удовлетворяет всем требованиям. Избегайте `--ignore-platform-reqs` в реальных проектах: флаг прячет настоящие несовместимости.

### Чем отличается `git merge` от `git rebase`?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:**

- **Merge** объединяет две ветки новым merge-коммитом (или fast-forward, если в целевой ветке нет новых коммитов). История сохраняется ровно такой, какой она была. Это неразрушающая операция, но история может стать запутанной.
- **Rebase** переносит ваши коммиты поверх другой ветки, создавая новые коммиты с новыми хешами. История становится линейной и чистой, но она **переписывается**.

Золотое правило: никогда не ребейзьте коммиты, которые уже забрали другие (общие ветки вроде `main`). Ребейзить свою фича-ветку, чтобы подтянуть изменения из `main` или причесать коммиты через `git rebase -i` перед открытием PR, — нормально. После ребейза уже запушенной ветки используйте `git push --force-with-lease` вместо `--force`: он откажется перезаписывать коммиты, которых вы не видели. Многие команды используют **squash merge**, который превращает весь PR в один коммит в `main`.
[Git: Merge vs Rebase vs Pull vs Fetch](../answers/git.md)

### Что такое Xdebug и для чего он нужен?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:** Xdebug — расширение PHP для отладки и анализа. В Xdebug 3 возможности включаются через `xdebug.mode`:

- `debug`: **пошаговая отладка** в IDE (PhpStorm, VS Code): брейкпоинты, просмотр переменных, step over/into. Расширение подключается к IDE по протоколу DBGp (порт по умолчанию **9003**).
- `develop`: улучшенный вывод `var_dump()` и стек-трейсы.
- `coverage`: покрытие кода для PHPUnit.
- `profile`: пишет cachegrind-файлы, по которым видно, на что уходит время (открываются в PhpStorm, KCachegrind или QCachegrind).
- `trace`: логирует каждый вызов функции.

```ini
xdebug.mode=debug
xdebug.start_with_request=trigger
xdebug.client_host=host.docker.internal
xdebug.client_port=9003
```

При `start_with_request=trigger` отладка запускается только при наличии cookie, GET/POST-параметра или переменной окружения `XDEBUG_TRIGGER` (или `XDEBUG_SESSION`). Xdebug заметно замедляет PHP, поэтому **на прод его не ставят никогда**. Если нужно только покрытие, **PCOV** работает намного быстрее.

### Для чего нужны Rector и PHP-CS-Fixer?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:**

- **PHP-CS-Fixer** автоматически исправляет **стиль кода**: форматирование, импорты, отступы — по наборам правил вроде `@PER-CS` или `@Symfony`. Альтернатива — **PHP_CodeSniffer**: `phpcs` находит нарушения, `phpcbf` их исправляет. **Laravel Pint** — обёртка над PHP-CS-Fixer без настройки.
- **Rector** выполняет **автоматический рефакторинг**, изменяя AST кода по правилам: апгрейд версии PHP (например, добавление constructor promotion, `readonly`, `match`), апгрейд фреймворков (Symfony, Laravel, PHPUnit), добавление объявлений типов и удаление мёртвого кода.

Оба инструмента обычно запускают в CI в режиме проверки (`php-cs-fixer fix --dry-run --diff`, `rector process --dry-run`), а локально или в pre-commit хуке — в режиме исправления. Вместе со статическим анализом (PHPStan/Psalm) они сильно удешевляют крупные апгрейды.

### Как разрешить конфликт зависимостей в Composer?

<span className="badge badge--warning margin-bottom--md">Senior</span>

**Ответ:** Конфликт означает, что ни одна комбинация версий не удовлетворяет всем ограничениям сразу. Шаги:

1. **Прочитать ошибку**: Composer выводит цепочку конфликтующих ограничений.
2. **Разобраться**: `composer why vendor/package` показывает, кто требует пакет, а `composer why-not vendor/package 3.0` — что мешает установить конкретную версию.
3. **Обновить вместе**: `composer update vendor/a vendor/b -w` (`--with-dependencies`) обновляет и их зависимости, а `-W` (`--with-all-dependencies`) обновляет их, даже если они перечислены в вашем корневом `require`.
4. **Ослабить или изменить свои ограничения** либо обновить или заменить пакет, который всех тормозит.
5. **Временные обходные пути**: inline-алиас (`"vendor/pkg": "dev-fix-branch as 1.4.0"`), чтобы использовать форк или ветку как релиз, либо форк в `repositories`.

Избегайте `--ignore-platform-reqs` и ручного редактирования lock-файла: они прячут проблемы, а не решают их.

### Что означают `provide`, `replace` и `conflict` в `composer.json`?

<span className="badge badge--warning margin-bottom--md">Senior</span>

**Ответ:**

- **`provide`**: пакет реализует виртуальный пакет или интерфейс. Например, `monolog/monolog` предоставляет `psr/log-implementation`, поэтому библиотека может требовать `psr/log-implementation`, а приложение — выбрать любой логгер.
- **`replace`**: пакет содержит код другого пакета, поэтому тот устанавливаться не будет. Например, монорепозиторий `symfony/symfony` заменяет отдельные компоненты `symfony/*`. Распространённый трюк — заменить ненужные на современной версии PHP полифилы: `"replace": {"symfony/polyfill-php80": "*"}`.
- **`conflict`**: указанные версии нельзя установить вместе с этим пакетом, например `"conflict": {"doctrine/orm": "<2.15"}`, если в старой версии известный баг.

### Как обеспечить безопасность зависимостей Composer?

<span className="badge badge--warning margin-bottom--md">Senior</span>

**Ответ:** Зависимости — это риск цепочки поставок (supply chain): вы запускаете код, который писали не вы.

- **`composer audit`** (Composer 2.4+) проверяет установленные пакеты по базе security advisories. Он также запускается автоматически после `composer update` и `composer require`. Добавьте его в CI.
- **`roave/security-advisories`**: мета-пакет, который «конфликтует» со всеми уязвимыми версиями, поэтому их просто невозможно установить.
- **Коммитьте `composer.lock`** и используйте `composer install` в CI и на проде, чтобы сборки использовали ровно проверенные версии.
- **`allow-plugins`**: разрешайте только доверенные плагины, ведь плагины выполняют код во время установки.
- **Автоматические обновления**: Dependabot или Renovate открывают PR с новыми версиями, а ваши тесты их проверяют.
- **Минимум зависимостей**: каждый пакет (и его транзитивные зависимости) увеличивает поверхность атаки. Перед добавлением проверяйте, поддерживается ли пакет и насколько он популярен.
- **Приватные пакеты**: используйте HTTPS-репозитории и храните учётные данные в `auth.json` или `COMPOSER_AUTH` (секрет в CI), но никогда не в `composer.json`.

### Как работать с приватными пакетами и монорепозиториями в Composer?

<span className="badge badge--warning margin-bottom--md">Senior</span>

**Ответ:** Дополнительные источники добавляются в секцию `repositories`:

- **`vcs`**: Git-репозиторий (GitHub, GitLab, Bitbucket). Composer читает теги и ветки как версии. Просто, но медленно при большом числе пакетов.
- **`composer`**: собственный реестр пакетов. **Satis** (self-hosted статический реестр), **Private Packagist** (SaaS) или реестры пакетов GitLab/GitHub.
- **`path`**: локальная директория, которая симлинкается в `vendor/`. Идеально для монорепозиториев и разработки пакета вместе с приложением.

```json
{
  "repositories": [
    { "type": "vcs", "url": "git@github.com:acme/billing-sdk.git" },
    { "type": "path", "url": "packages/*", "options": { "symlink": true } }
  ],
  "require": {
    "acme/billing-sdk": "^2.1",
    "acme/shared-kernel": "*@dev"
  }
}
```

Учётные данные хранят в `auth.json` (добавленном в `.gitignore`) или в переменной окружения `COMPOSER_AUTH` в CI. Большие монорепозитории часто используют split-инструмент (например, `splitsh-lite`), чтобы публиковать каждый пакет в отдельный read-only репозиторий, как это делают Symfony и Laravel.

### Как профилировать PHP-приложение, в том числе на проде?

<span className="badge badge--warning margin-bottom--md">Senior</span>

**Ответ:** Сначала измеряем, потом оптимизируем. Инструменты:

- **Профайлер Xdebug** (`xdebug.mode=profile`): очень подробный, но с большим оверхедом. Только для локальной разработки.
- **Blackfire**: коммерческий профайлер с профилированием по запросу, графами вызовов, сравнением запусков и performance-ассертами в CI. Безопасен для прода, потому что профилирование включается только для конкретных запросов.
- **Tideways / XHProf / SPX**: лёгкие профайлеры. Tideways — коммерческий APM с непрерывным сэмплированием, XHProf (изначально от Facebook) — open source, SPX — open source со встроенным веб-интерфейсом.
- **APM** (New Relic, Datadog, инструменты на базе OpenTelemetry): непрерывный мониторинг времени ответа, медленных транзакций, запросов к БД и внешних вызовов по всем запросам.

На практике APM показывает, **какие** эндпоинты медленные, а профайлер — **почему** (медленный SQL и N+1 запросы, тяжёлые циклы, гидрация слишком большого числа объектов, медленные внешние API). Типичные находки в PHP-приложениях: N+1 запросы, отсутствующие индексы, отсутствие кэша и медленная автозагрузка (лечится оптимизированным автозагрузчиком и OPcache).

# 21. Elasticsearch

### Каковы основные понятия Elasticsearch: кластер, нода, индекс, документ, шард, реплика?

<span className="badge badge--success margin-bottom--md">Junior</span>

**Ответ:**

- **Кластер (cluster)**: группа нод, которые работают вместе и делят данные. Идентифицируется по имени.
- **Нода (node)**: отдельный сервер Elasticsearch (JVM-процесс). У нод есть роли: master-eligible, data, ingest, coordinating и др.
- **Индекс (index)**: коллекция документов со схожей структурой, примерно как таблица в реляционной БД (`products`, `logs-2026.11.15`).
- **Документ (document)**: JSON-объект, хранящийся в индексе и идентифицируемый по `_id`, примерно как строка.
- **Маппинг (mapping)**: схема индекса: имена и типы полей и то, как они анализируются.
- **Шард (shard)**: индекс делится на **первичные шарды (primary shards)**, каждый из которых — отдельный индекс Lucene. Шарды распределяются по нодам, что даёт горизонтальное масштабирование.
- **Реплика (replica)**: копия первичного шарда на другой ноде. Реплики обеспечивают отказоустойчивость и тоже обслуживают поисковые запросы, увеличивая пропускную способность чтения.

Начиная с Elasticsearch 7.0 у индекса только один тип маппинга (старая аналогия «индекс = база данных, тип = таблица» устарела), а в 8.0 типы удалены полностью.

### Когда стоит использовать Elasticsearch и почему он не должен быть основной базой данных?

<span className="badge badge--success margin-bottom--md">Junior</span>

**Ответ:** Elasticsearch хорош для:

- **Полнотекстового поиска** с ранжированием по релевантности, устойчивостью к опечаткам, синонимами, стеммингом и подсветкой.
- **Фасетного поиска и фильтрации** в каталогах (фильтры по бренду, цене и атрибутам со счётчиками).
- **Аналитики логов и метрик** (ELK / Elastic Stack: Elasticsearch, Logstash/Beats, Kibana).
- **Агрегаций** по большим объёмам данных почти в реальном времени.

Обычно он не должен быть **основным источником истины**:

- Нет ACID-транзакций на несколько документов и нет JOIN'ов (есть только ограниченные типы полей `nested` и `join`).
- **Near real-time**: новый документ становится доступен для поиска только после refresh (по умолчанию через 1 секунду).
- Смена типа поля требует полной переиндексации.
- Он спроектирован как индекс, который можно перестроить, а не как система учёта: нет ограничений целостности и внешних ключей, а бэкапы делаются через снапшоты.

Типичная схема: MySQL/PostgreSQL — источник истины, а Elasticsearch — **оптимизированный для чтения поисковый индекс**, который синхронизируется из БД и может быть перестроен в любой момент.

### Что такое инвертированный индекс (Inverted Index)?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:** Основная структура данных Elasticsearch, которая сопоставляет термины (слова) с документами, в которых они встречаются, что обеспечивает очень быстрый поиск.

### Что такое анализаторы (Analyzers)?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:** Компоненты, обрабатывающие текст при индексации или поиске. Они состоят из символьного фильтра (Character Filter), токенизатора (Tokenizer) и фильтра токенов (Token Filter).

### Чем отличаются типы полей `text` и `keyword`?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:**

- **`text`**: значение **анализируется**, то есть разбивается на токены, приводится к нижнему регистру, стеммится и т. д. Используется для полнотекстового поиска (запросы `match`) по заголовкам, описаниям и статьям. Для сортировки и агрегаций эффективно не подходит.
- **`keyword`**: значение хранится **как есть**, одним точным токеном. Используется для точного совпадения (запросы `term`), фильтров, сортировки и агрегаций: статусы, теги, email, ID и артикулы.

Если проиндексировать строку без явного маппинга, динамический маппинг создаст оба варианта: поле `text` и подполе `.keyword` (с `ignore_above: 256`). Лучше задавать маппинг явно:

```json
{
  "mappings": {
    "properties": {
      "title": { "type": "text", "fields": { "raw": { "type": "keyword" } } },
      "status": { "type": "keyword" },
      "price": { "type": "scaled_float", "scaling_factor": 100 }
    }
  }
}
```

### Чем отличаются запросы `match` и `term`?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:**

- **`match`**: **полнотекстовый** запрос. Поисковая строка проходит через тот же анализатор, что и поле, а полученные токены ищутся в инвертированном индексе. `match` по `title` со строкой "Red Shoes" найдёт документы, содержащие "red" или "shoes" (чтобы требовать оба слова, используйте `"operator": "and"`).
- **`term`**: **точный** запрос без анализа. Ищет ровно заданный токен. Предназначен для полей `keyword`, числовых полей, дат и boolean.

Классический баг: `term`-запрос "Red Shoes" по полю `text` ничего не находит, потому что в индексе лежат токены "red" и "shoes" в нижнем регистре, а не исходная строка. Используйте `term` для полей `keyword` и `match` для полей `text`.

### Чем отличается query context от filter context? Как работает запрос `bool`?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:**

- **Query context** отвечает на вопрос «**насколько хорошо** документ подходит?» и вычисляет оценку релевантности (`_score`).
- **Filter context** отвечает на вопрос «**подходит ли** документ: да или нет?». Оценка не вычисляется, а результаты часто используемых фильтров **кэшируются**, поэтому фильтры быстрее.

Запрос `bool` комбинирует условия:

- `must`: должно совпасть и влияет на оценку (query context).
- `should`: повышает оценку при совпадении. Если нет `must` и `filter`, должно совпасть хотя бы одно `should` (`minimum_should_match`).
- `filter`: должно совпасть, без оценки, кэшируется.
- `must_not`: не должно совпасть (filter context).

Правило: полнотекстовые условия кладём в `must`/`should`, а точные (статус, категория, диапазон цен, даты) — в `filter`.

```json
{
  "query": {
    "bool": {
      "must": [{ "match": { "title": "running shoes" } }],
      "filter": [
        { "term": { "status": "active" } },
        { "range": { "price": { "gte": 50, "lte": 150 } } }
      ],
      "must_not": [{ "term": { "brand": "noname" } }]
    }
  }
}
```

### Как в Elasticsearch вычисляется релевантность?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:** Начиная с версии 5.0 Elasticsearch по умолчанию использует **BM25** — улучшенную версию TF-IDF. Оценка документа зависит от:

- **Частоты термина (TF)**: как часто термин встречается в поле. Больше вхождений — выше оценка, но с насыщением: 100 вхождений не в 100 раз лучше одного.
- **Обратной частоты документа (IDF)**: насколько термин редок в индексе. Редкие термины ("elasticsearch") весят больше частых ("the").
- **Длины поля**: совпадение в коротком поле (заголовке) весит больше, чем в длинном (тексте статьи).

На оценку можно влиять через **бустинг** (`"title^3"` в `multi_match`), `function_score` (например, буст по популярности, свежести или расстоянию) и `rescore`. Чтобы понять, почему документ получил свою оценку, используйте `"explain": true`. Учтите, что IDF считается на уровне шарда, поэтому при малом числе документов оценки могут выглядеть непоследовательно.

### Как делать глубокую пагинацию в Elasticsearch?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:**

- **`from` + `size`**: просто, но каждый шард должен вернуть координирующей ноде `from + size` документов, а она сортирует их все. Стоимость растёт с глубиной, поэтому по умолчанию действует лимит `from + size <= 10000` (`index.max_result_window`). Подходит для первых страниц в интерфейсе.
- **`search_after`** + **Point in Time (PIT)**: рекомендуемый способ глубокой пагинации. Вы передаёте значения сортировки последнего документа предыдущей страницы, поэтому каждая страница одинаково дешёвая. PIT сохраняет консистентный снимок индекса между запросами. Перейти на произвольный номер страницы нельзя — это аналог keyset-пагинации в SQL.
- **`scroll`**: старый способ выгрузки больших объёмов. Для глубокой пагинации больше не рекомендуется, вместо него используйте `search_after` с PIT.

Увеличивать `max_result_window` до миллионов — плохая идея: это может исчерпать heap.

### Что такое агрегации в Elasticsearch?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:** Агрегации вычисляют аналитику по документам, найденным запросом, — аналог `GROUP BY` и агрегатных функций в SQL, но в одном запросе вместе с поиском:

- **Метрические агрегации**: `avg`, `sum`, `min`, `max`, `stats`, `cardinality` (приблизительный подсчёт уникальных значений, HyperLogLog++), `percentiles`.
- **Bucket-агрегации**: группируют документы в корзины. `terms` (по значению поля), `range`, `date_histogram` (по временному интервалу), `histogram`, `filters`.
- **Pipeline-агрегации**: работают с результатами других агрегаций (`derivative`, `moving_fn`, `bucket_sort`).

Агрегации можно вкладывать друг в друга, например продажи по категориям (`terms`) по месяцам (`date_histogram`) со средней ценой (`avg`). Типичный пример — фасеты в интернет-магазине: «Бренд: Nike (120), Adidas (95)». Агрегациям нужны поля `keyword`, числовые поля или даты (doc values). `terms`-агрегации по полям с высокой кардинальностью приблизительны и могут потреблять много памяти.

### Как эффективно индексировать данные в Elasticsearch из PHP?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:** Используйте официальный клиент `elasticsearch/elasticsearch` и **Bulk API**: отправка документов по одному — это один HTTP-запрос на документ, а `_bulk` отправляет тысячи операций одним запросом.

```php
use Elastic\Elasticsearch\ClientBuilder;

$client = ClientBuilder::create()->setHosts(['http://localhost:9200'])->build();

$params = ['body' => []];
foreach ($products as $i => $product) {
    $params['body'][] = ['index' => ['_index' => 'products', '_id' => $product['id']]];
    $params['body'][] = ['title' => $product['title'], 'price' => $product['price']];

    if (($i + 1) % 1000 === 0) {
        $response = $client->bulk($params);
        $params = ['body' => []];
    }
}
if ($params['body'] !== []) {
    $response = $client->bulk($params);
}
```

Советы:

- Держите размер bulk-запроса в районе 5–15 МБ и подбирайте его экспериментально.
- **Проверяйте ответ на ошибки**: `_bulk` возвращает HTTP 200, даже если часть операций упала (`errors: true` в теле ответа).
- Для большого первичного импорта выставьте `refresh_interval` в `-1` и `number_of_replicas` в `0`, а после импорта верните оба значения.

### Что означают статусы здоровья кластера green, yellow и red?

<span className="badge badge--primary margin-bottom--md">Middle</span>

**Ответ:** `GET _cluster/health` возвращает:

- **Green**: все первичные шарды и реплики размещены. Всё в порядке.
- **Yellow**: все первичные шарды размещены, но часть реплик — нет. Все данные доступны, но отказоустойчивость снижена. Типичный случай — кластер из одной ноды с `number_of_replicas: 1`, ведь реплику нельзя разместить на той же ноде, что и её первичный шард.
- **Red**: как минимум один первичный шард не размещён, поэтому часть данных недоступна, и поиск по этому индексу возвращает неполные результаты или ошибки.

Для расследования используйте `GET _cat/shards?v`, `GET _cat/indices?v&health=red` и `GET _cluster/allocation/explain`. Частые причины: упавшая нода, заполненный диск (disk watermarks: по умолчанию low 85% и high 90%, а при 95% срабатывает flood stage и индексы становятся read-only) или невыполнимые правила размещения.

### Как синхронизировать Elasticsearch с основной базой данных?

<span className="badge badge--warning margin-bottom--md">Senior</span>

**Ответ:**

- **Двойная запись (dual write)**: приложение пишет в БД, а затем в Elasticsearch. Просто, но ненадёжно: если вторая запись не удалась или процесс упал, данные расходятся, а атомарности между двумя системами нет.
- **Асинхронная индексация через очередь**: после коммита в БД публикуется событие (`ProductUpdated`), а воркер перечитывает сущность из БД и индексирует её. Сбои обрабатываются ретраями и DLQ. Чтобы событие гарантированно не потерялось, используют паттерн **Transactional Outbox**: событие пишется в таблицу `outbox` в той же транзакции БД, а затем публикуется отдельным релеем.
- **CDC (Change Data Capture)**: инструмент вроде **Debezium** читает binlog/WAL базы и стримит изменения в Kafka, а консьюмер их индексирует. Ничего не теряется, даже если изменение прошло мимо кода приложения, но добавляется инфраструктура.
- **Периодическая пакетная синхронизация**: переиндексация записей, изменённых после `updated_at` (cron, Logstash JDBC input). Просто, но добавляет задержку и пропускает физические удаления.

Во всех случаях: индексируйте **идемпотентно** (используйте первичный ключ БД как `_id`), защищайтесь от обновлений, пришедших не по порядку (параметры `version` + `version_type: external` или перечитывание актуального состояния из БД), и держите наготове процедуру **полной переиндексации** для восстановления.

### Как изменить маппинг без даунтайма?

<span className="badge badge--warning margin-bottom--md">Senior</span>

**Ответ:** Тип существующего поля изменить нельзя (можно только добавлять новые поля), потому что данные уже проиндексированы определённым образом. Решение — **переиндексация за алиасом**:

1. Приложение всегда работает с **алиасом** (`products`), а не с конкретным индексом (`products_v1`).
2. Создаём новый индекс `products_v2` с новым маппингом.
3. Копируем данные: через `_reindex` API (внутри кластера) или полным реимпортом из основной БД.
4. Догоняем изменения, сделанные во время переиндексации: пишем в оба индекса или переигрываем изменения из очереди либо по `updated_at`.
5. Атомарно переключаем алиас:

```json
POST _aliases
{
    "actions": [
        { "remove": { "index": "products_v1", "alias": "products" } },
        { "add":    { "index": "products_v2", "alias": "products" } }
    ]
}
```

6. После проверки удаляем старый индекс. Откат — это просто переключение алиаса обратно.

Чтобы избежать сюрпризов, запретите неожиданные поля через `"dynamic": "strict"` (или используйте явные `dynamic_templates`): динамический маппинг может угадать неверный тип, а «взрыв маппинга» (тысячи полей) способен замедлить весь кластер.

### Как выбрать количество шардов и реплик?

<span className="badge badge--warning margin-bottom--md">Senior</span>

**Ответ:**

- **Первичные шарды** определяют, как делятся данные. Их число задаётся при создании индекса и не может быть изменено позже без переиндексации (кроме `_split` и `_shrink` API). Начиная с версии 7 по умолчанию 1.
- **Реплики** можно менять в любой момент. Они дают отказоустойчивость и увеличивают пропускную способность поиска, но каждая реплика стоит диска и ресурсов на индексацию.

Рекомендации:

- Ориентируйтесь на размер шарда примерно **10–50 ГБ** (и меньше ~200 млн документов на шард).
- **Оверщардинг** — частая ошибка: каждый шард расходует heap, файловые дескрипторы и место в cluster state, а поиск расходится по всем шардам. Сотни крошечных шардов медленнее нескольких крупных.
- Для данных, привязанных ко времени (логи, события), используйте **data streams / rollover** с **ILM** (Index Lifecycle Management): переход на новый индекс по размеру или возрасту и перемещение старых индексов по фазам hot → warm → cold → delete.
- На проде используйте минимум 3 master-eligible ноды для кворума и хотя бы 1 реплику.

### Почему документ не находится сразу после индексации? Объясните refresh, flush и translog.

<span className="badge badge--warning margin-bottom--md">Senior</span>

**Ответ:** Elasticsearch работает в режиме **near real-time**:

1. Новый документ пишется в буфер в памяти и в **translog** (журнал транзакций на диске для надёжности).
2. **Refresh** (по умолчанию каждую секунду, `refresh_interval`) превращает буфер в новый **сегмент** Lucene, видимый для поиска. Только после этого документ можно найти. При этом `GET` по `_id` работает в реальном времени.
3. **Flush** выполняет коммит Lucene: сегменты сбрасываются на диск через fsync, а translog очищается.
4. В фоне мелкие сегменты **сливаются (merge)** в крупные, а удалённые документы вычищаются.

Практические следствия:

- В тестах или когда пользователь должен сразу увидеть своё изменение, используйте `?refresh=wait_for` в запросе на запись. Избегайте `?refresh=true` под нагрузкой: он создаёт много крошечных сегментов.
- При интенсивной индексации увеличьте `refresh_interval` (например, до `30s`) или отключите его на время bulk-импорта.
- Обновления и удаления не меняют документ на месте: Elasticsearch помечает старую версию удалённой и пишет новую, поэтому часто обновляемые документы (например, счётчики) обходятся дорого.

### Как реализовать автодополнение и поиск, устойчивый к опечаткам?

<span className="badge badge--warning margin-bottom--md">Senior</span>

**Ответ:**

- **Нечёткий поиск (fuzzy)**: `match` с `"fuzziness": "AUTO"` прощает опечатки на основе расстояния Левенштейна (0 правок для коротких слов, до 2 для длинных). Подходит для случаев вроде "iphnoe" → "iphone".
- **Edge n-grams**: при индексации кастомный анализатор разбивает слова на префиксы ("lap", "lapt", "lapto", "laptop"). Поиск по префиксу превращается в простой поиск термина — быстро и гибко, но индекс растёт. При поиске используйте стандартный анализатор, чтобы запрос тоже не разбивался на n-граммы.
- **Тип поля `search_as_you_type`**: встроенный тип, который автоматически создаёт подполя с шинглами и edge n-граммами. Запрашивается через `multi_match` с типом `bool_prefix`.
- **Completion suggester**: отдельное поле `completion`, хранящееся в структуре FST в памяти. Самый быстрый вариант для подсказок в строке поиска, но поддерживает только поиск по префиксу, и его сложнее обновлять и фильтровать.
- **Синонимы и языковые анализаторы**: фильтры синонимов ("tv" ↔ "television") и стеммеры для конкретного языка (например, анализатор `russian`) улучшают полноту поиска.

На практике их комбинируют: n-граммы или `search_as_you_type` для подсказок, `match` с fuzziness для основного поиска и бустинг точных совпадений, чтобы они ранжировались выше нечётких.

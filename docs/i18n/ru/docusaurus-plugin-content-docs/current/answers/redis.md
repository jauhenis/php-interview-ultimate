# Redis: паттерны кэширования, персистентность и масштабирование

[Документация Redis](https://redis.io/docs/latest/)

Redis — это in-memory хранилище «ключ — значение». Помимо кэша, PHP-приложения используют его для хранения сессий (`session.save_handler = redis` с расширением phpredis), как бэкенд очередей (очереди Laravel, Symfony Messenger), для счётчиков и rate limiting (`INCR`), распределённых блокировок (`SET key token NX PX 30000`) и обмена сообщениями (Pub/Sub, Streams).

Примеры ниже написаны на чистом PHP 8.1+ без фреймворка, с расширением [phpredis](https://github.com/phpredis/phpredis) (`ext-redis`). `$redis` — подключённый экземпляр `Redis`:

```php
$redis = new Redis();
$redis->connect('127.0.0.1', 6379);
```

## Время жизни ключа (TTL)

Время жизни задаётся через `SET key value EX 60`, `EXPIRE key 60`, `PEXPIRE` (в миллисекундах) или `EXPIREAT` (Unix timestamp). `TTL key` возвращает оставшиеся секунды, `-1`, если у ключа нет срока жизни, и `-2`, если ключа не существует. `PERSIST` снимает срок жизни. Обычный `SET` для существующего ключа тоже сбрасывает TTL, если не передать `KEEPTTL`.

Redis удаляет истёкшие ключи двумя способами. Когда клиент обращается к истёкшему ключу, Redis удаляет его и ничего не возвращает. Кроме того, фоновый цикл выбирает ключи с TTL и удаляет истёкшие. Поэтому истёкший ключ может ещё недолго занимать память.

## Почему Redis быстрый

Данные хранятся в оперативной памяти, поэтому чтение не требует дискового ввода-вывода. Один поток выполняет команды по очереди, поэтому командам не нужны блокировки, и каждая команда атомарна. Мультиплексирование ввода-вывода (epoll или kqueue) позволяет этому потоку обслуживать тысячи соединений. Начиная с Redis 6, настройка `io-threads` выносит сетевое чтение и запись в дополнительные потоки, но команды по-прежнему выполняются по одной. Медленная команда, например `KEYS *` или `HGETALL` на огромном хеше, задерживает всех остальных клиентов.

## Стратегии кэширования

- **Cache-aside (ленивая загрузка):** приложение читает из кэша. При промахе оно загружает данные из БД и записывает их в кэш. В кэш попадают только запрошенные данные, но до истечения TTL они могут быть устаревшими.
- **Read-through:** слой кэша сам загружает недостающие данные, а приложение обращается только к кэшу.
- **Write-through:** каждая запись синхронно обновляет и кэш, и БД. Кэш всегда актуален, но запись медленнее.
- **Write-behind (write-back):** запись идёт в кэш и попадает в БД позже, часто пачками. Запись быстрая, но данные теряются, если кэш упадёт до сброса в БД.
- **Refresh-ahead:** часто читаемые ключи обновляются в фоне до истечения срока жизни.

Cache-aside с phpredis и PDO:

```php
function findUser(Redis $redis, PDO $pdo, int $id): ?array
{
    $key = "user:{$id}";

    $cached = $redis->get($key);
    if ($cached !== false) {
        return json_decode($cached, true);
    }

    $stmt = $pdo->prepare('SELECT id, name, email FROM users WHERE id = ?');
    $stmt->execute([$id]);
    $user = $stmt->fetch(PDO::FETCH_ASSOC) ?: null;

    if ($user !== null) {
        $redis->set($key, json_encode($user), ['ex' => 3600]);
    }

    return $user;
}
```

Фреймворки реализуют тот же паттерн: `Cache::remember()` в Laravel и `CacheInterface::get($key, $callback)` в компоненте Symfony Cache.

## Инвалидация кэша

- **TTL:** данные могут быть устаревшими не дольше TTL.
- **Удаление при записи:** после коммита транзакции в БД удаляйте ключ, а не записывайте новое значение. Если два процесса одновременно обновляют кэш, последним может записаться более старое значение. Удаление не оставляет в кэше устаревших данных.
- **Версионированные ключи:** добавьте в ключ версию, например `catalog:v42:product:1`. После увеличения версии старые ключи становятся недоступны и удаляются по TTL.
- **Теги:** группируйте ключи по тегу и сбрасывайте всю группу, например через `TagAwareCacheInterface::invalidateTags()` в Symfony или `Cache::tags()` в Laravel.

Читающий процесс всё ещё может загрузить старую строку до коммита и записать её в кэш после удаления. Короткий TTL ограничивает время, которое такое значение проведёт в кэше.

## Лимит памяти и вытеснение

Когда потребление памяти достигает `maxmemory`, Redis применяет `maxmemory-policy`:

- `noeviction` (по умолчанию): запись завершается ошибкой OOM, чтение работает.
- `allkeys-lru` / `volatile-lru`: вытесняется ключ, который дольше всех не использовался, среди всех ключей или среди ключей с TTL.
- `allkeys-lfu` / `volatile-lfu`: вытесняется наименее часто используемый ключ.
- `allkeys-random` / `volatile-random`: вытесняется случайный ключ.
- `volatile-ttl`: вытесняется ключ с наименьшим оставшимся TTL.

Для Redis, который служит только кэшем, обычно выбирают `allkeys-lru` или `allkeys-lfu`. Если в том же экземпляре хранятся сессии, очереди или блокировки, вытеснение может их удалить. Используйте отдельный экземпляр или политику `volatile-*`, задавая TTL только ключам кэша. Если ни у одного ключа нет TTL, политики `volatile-*` ведут себя как `noeviction`.

## Персистентность: RDB и AOF

- **RDB:** Redis периодически сохраняет снимок всего набора данных из дочернего процесса, созданного через fork (правила `save`, `BGSAVE`). Файлы компактные и быстро загружаются, но записи после последнего снимка теряются. Fork большого набора данных может вызывать всплески задержки.
- **AOF:** Redis дописывает каждую команду записи в журнал. `appendfsync` управляет надёжностью: `always` — самый надёжный и медленный вариант, `everysec` (по умолчанию) теряет не больше секунды записей, `no` оставляет сброс на диск операционной системе. Фоновая перезапись сжимает журнал.
- **RDB и AOF вместе:** с `aof-use-rdb-preamble yes` (по умолчанию начиная с Redis 5) перезаписанный AOF начинается со снимка RDB, поэтому перезапуск быстрее.
- **Без персистентности:** допустимо для кэша, который можно восстановить из БД.

Репликация асинхронная, поэтому даже с `appendfsync always` Redis не должен хранить единственную копию критичных данных.

## Команды, которые блокируют Redis

`KEYS` обходит все ключи за один вызов. При миллионах ключей он может заблокировать сервер на секунды. `SCAN` перебирает ключи с курсором и возвращает небольшие порции. Он может вернуть ключ несколько раз, а ключи, добавленные или удалённые во время обхода, могут не попасть в результат. `HSCAN`, `SSCAN` и `ZSCAN` перебирают элементы одного хеша, множества и сортированного множества.

Удаление ключей по шаблону с phpredis:

```php
$redis->setOption(Redis::OPT_SCAN, Redis::SCAN_RETRY);

$iterator = null;
while ($keys = $redis->scan($iterator, 'session:*', 1000)) {
    $redis->unlink($keys);
}
```

Другие команды, которые могут заблокировать Redis: `DEL` для огромного ключа (используйте `UNLINK`, который освобождает память в фоновом потоке), `FLUSHALL` / `FLUSHDB` без `ASYNC`, а также `HGETALL`, `SMEMBERS` или `LRANGE 0 -1` на больших коллекциях. `redis-cli --bigkeys` находит большие ключи, а `SLOWLOG GET` показывает медленные команды.

## Pipelining и транзакции

- **Pipelining** отправляет много команд, не дожидаясь ответа на каждую. Это экономит сетевые round trip, но между командами могут выполниться команды других клиентов.
- **`MULTI`/`EXEC`** накапливает команды и выполняет их единым изолированным блоком. Если команда падает во время выполнения, например `INCR` для нечислового значения, остальные команды всё равно применяются. Ошибки, обнаруженные при постановке в очередь, например неверное число аргументов, отменяют всю транзакцию.
- **`WATCH`** отменяет транзакцию, если отслеживаемый ключ изменился до `EXEC`, и клиент повторяет её.
- **Lua-скрипты** (`EVAL`) выполняются на сервере атомарно и подходят для логики «прочитать, решить, записать».

С phpredis:

```php
// Pipelining: один сетевой round trip
$pipe = $redis->pipeline();
foreach ([1, 2, 3] as $id) {
    $pipe->get("user:{$id}");
}
$users = $pipe->exec();

// Транзакция: обе команды выполняются единым блоком
$pageId = 42;
$redis->multi()
    ->incr("views:{$pageId}")
    ->expire("views:{$pageId}", 86400)
    ->exec();
```

## PHP-клиенты: phpredis и Predis

- **phpredis** — расширение PHP, написанное на C (`pecl install redis`). Оно быстрее и поддерживает постоянные соединения, бинарные сериализаторы и сжатие. Его нужно установить на каждый сервер и в каждый Docker-образ.
- **Predis** — Composer-пакет, написанный на PHP (`composer require predis/predis`). Ему не нужно расширение, но он медленнее.

Laravel и компонент Symfony Cache поддерживают оба клиента.

## Cache stampede

Когда истекает часто читаемый ключ, множество параллельных запросов одновременно получают промах и выполняют один и тот же тяжёлый запрос. Способы защиты:

- **Блокировка:** значение пересчитывает только процесс, получивший `SET lock:key token NX EX 10`. Остальные недолго ждут или возвращают старое значение. В Laravel есть `Cache::lock()`, а компонент Symfony Cache автоматически блокирует вычисление отсутствующего значения.
- **Вероятностное раннее обновление:** запрос может пересчитать значение до истечения TTL с вероятностью, которая растёт по мере приближения срока. Компонент Symfony Cache поддерживает это через аргумент `$beta` метода `get()`.
- **Stale-while-revalidate:** отдавайте старое значение, пока оно обновляется в фоне, например через `Cache::flexible()` в Laravel 11+.
- **Фоновое обновление:** задача по расписанию обновляет ключ до его истечения.

## Cache penetration, breakdown и avalanche

- **Penetration:** запросы к несуществующим данным, например случайные ID от бота, никогда не попадают в кэш и всегда доходят до БД. Кэшируйте пустой результат с коротким TTL, валидируйте входные данные или проверяйте ID по фильтру Блума.
- **Breakdown:** истекает один часто читаемый ключ, что вызывает stampede. См. предыдущий раздел.
- **Avalanche:** одновременно истекает много ключей, потому что их записали с одинаковым TTL, или узел кэша перезапускается пустым. Добавляйте к TTL случайный разброс (`3600 + random_int(0, 300)`), используйте реплики и персистентность и прогревайте кэш постепенно.

## Sentinel и Cluster

Оба решения используют асинхронную репликацию с мастера на реплики, поэтому запись, подтверждённая мастером, может потеряться, если мастер упадёт до её репликации.

- **Sentinel** следит за одним мастером и его репликами. Когда достаточно процессов Sentinel соглашаются, что мастер недоступен, они повышают реплику до мастера и сообщают клиентам её адрес. Sentinel не шардирует данные, поэтому весь набор данных должен помещаться на одном мастере.
- **Cluster** делит пространство ключей на 16384 хеш-слота, распределённые между несколькими мастерами с репликами, и сам выполняет failover. Команды с несколькими ключами, транзакции и Lua-скрипты работают, только если все ключи находятся в одном слоте. Хеш-теги помещают связанные ключи в один слот: в `{user:42}:profile` и `{user:42}:cart` хешируется только `user:42`. Cluster поддерживает только базу 0, а клиенты должны обрабатывать перенаправления `MOVED` и `ASK`. В phpredis для этого есть класс `RedisCluster`.

Выбирайте Sentinel, если данные помещаются на один узел и нужен автоматический failover. Выбирайте Cluster, если нужно масштабировать память или пропускную способность записи на несколько узлов.

## Rate limiting

- **Фиксированное окно:** увеличивайте через `INCR` ключ вида `rate:{userId}:{minute}` и задавайте ему TTL при первом запросе. На границе окон такой лимитер пропускает до двух лимитов.
- **Скользящее окно (лог):** сортированное множество с метками времени запросов. Удаляйте старые записи через `ZREMRANGEBYSCORE`, считайте оставшиеся через `ZCARD` и добавляйте новый запрос через `ZADD`. Способ точный, но расход памяти растёт с числом запросов.
- **Token bucket:** плавное ограничение с постоянным расходом памяти, обычно реализуется на Lua.

`INCR` и `EXPIRE` должны выполняться атомарно. Если процесс остановится между ними, ключ никогда не истечёт и пользователь останется заблокированным. Фиксированное окно в Lua-скрипте с phpredis:

```php
$script = <<<'LUA'
local current = redis.call('INCR', KEYS[1])
if current == 1 then
    redis.call('EXPIRE', KEYS[1], ARGV[1])
end
return current
LUA;

$userId = 42;
$key = sprintf('rate:%d:%d', $userId, intdiv(time(), 60));
$count = $redis->eval($script, [$key, 60], 1);

if ($count > 100) {
    http_response_code(429);
    exit;
}
```

Lua-скрипт блокирует Redis на время выполнения, поэтому скрипты должны быть короткими. В Laravel есть фасад `RateLimiter`, а в Symfony — компонент RateLimiter. Оба могут хранить состояние в Redis.

## Pub/Sub и Streams

- **Pub/Sub:** `PUBLISH` доставляет сообщение только подписчикам, подключённым в этот момент. Redis не хранит сообщение, поэтому отключённый подписчик его пропустит. Подходит для уведомлений в реальном времени и инвалидации кэша на нескольких серверах.
- **Streams:** `XADD` дописывает записи в персистентный журнал. Группы потребителей (`XREADGROUP`) распределяют записи между воркерами, и каждый воркер подтверждает запись через `XACK`. Неподтверждённые записи остаются в ожидании, и другой воркер может забрать их через `XAUTOCLAIM`. Сообщение может быть доставлено повторно, поэтому обработчики должны быть идемпотентными. Ограничивайте длину стрима через `MAXLEN` или `MINID`. Redis-транспорт Symfony Messenger построен на Streams.

Подписка и блокирующее чтение должны выполняться в долгоживущем CLI-воркере, а не в запросе PHP-FPM.

# Highload и масштабирование на практике

Это руководство посвящено практической стороне работы PHP-приложения под высокой нагрузкой. Архитектурные темы — микросервисы, CQRS, шардирование — разобраны в руководстве [Архитектура и Highload](architecture_highload.md).

## CDN

CDN (Content Delivery Network) — сеть edge-серверов, которые кэшируют контент рядом с пользователями. Запросы к закэшированным файлам обслуживает ближайший edge-сервер, а не ваш origin-сервер.

- **Меньше задержка:** JS, CSS, изображения и видео приходят из ближайшей точки.
- **Меньше нагрузка на origin:** большинство запросов к статике не доходит до ваших серверов.
- **Дополнительная защита:** большинство CDN также предлагают защиту от DDoS, терминацию TLS и web application firewall.

Кэшированием управляют HTTP-заголовки, например `Cache-Control: public, max-age=31536000, immutable`. Добавляйте хеш содержимого в имена статических файлов (`app.3f9a1c.js`): тогда файл можно кэшировать на год, а каждый деплой ссылается на новые имена. CDN может кэшировать и публичные HTML-страницы и ответы API через `s-maxage`, но персонализированные ответы публично кэшировать нельзя.

## Stateless-серверы приложений

Stateless-сервер не хранит данные между запросами в памяти или на локальном диске. Тогда любой запрос может попасть на любой сервер, а балансировщик может свободно добавлять и убирать серверы.

| Состояние            | Где хранить                                                                                           |
| -------------------- | ----------------------------------------------------------------------------------------------------- |
| Сессии               | Redis, Memcached или БД либо подписанный токен, например JWT                                          |
| Загруженные файлы    | Объектное хранилище, например S3 или MinIO                                                            |
| Кэш                  | Общий кэш, например Redis. APCu — только для данных, которые могут немного отличаться между серверами |
| Задачи по расписанию | Один планировщик или распределённая блокировка, чтобы задача не запускалась на каждом сервере         |
| Логи                 | Централизованная система, например ELK или Loki                                                       |

PHP-FPM следует модели share-nothing: каждый запрос начинается с чистой памяти. Это одна из причин, почему PHP-приложения легко масштабируются горизонтально.

## Фоновые очереди

Веб-запрос должен выполнять только ту работу, которую пользователь обязан дождаться. Отправку писем, генерацию PDF, обработку изображений и вызовы медленных внешних API выносят в очередь, которую обрабатывают воркеры:

- Пользователь сразу получает ответ.
- Если внешний API недоступен, задача повторяется позже, а не ломает запрос.
- Всплески трафика заполняют очередь, а не перегружают серверы.
- Воркеры масштабируются отдельно от веб-серверов.

В PHP обычно используют Laravel Queues и Symfony Messenger с RabbitMQ, Redis, Amazon SQS или Kafka в качестве транспорта. Долгоживущие воркеры не ограничены таймаутами PHP-FPM, но в них может течь память, поэтому их периодически перезапускают.

## Настройка PHP-FPM

Ключевые настройки в конфигурации пула, например `www.conf`:

```ini
pm = static
pm.max_children = 100
pm.max_requests = 1000
request_terminate_timeout = 30s
request_slowlog_timeout = 5s
slowlog = /var/log/php-fpm/slow.log
pm.status_path = /fpm-status
```

- **`pm`:** `static` держит фиксированное число воркеров и подходит для выделенных серверов. `dynamic` держит диапазон простаивающих воркеров. `ondemand` запускает воркеры только при поступлении запросов и подходит для сайтов с небольшим трафиком.
- **`pm.max_children`:** максимальное число запросов, обрабатываемых параллельно. Оценивайте его как память, доступную PHP, делённую на средний расход памяти одним воркером: 8 ГБ / 80 МБ — около 100 воркеров. Слишком много воркеров приводит к свопу, слишком мало — к ожиданию запросов.
- **`pm.max_requests`:** перезапускает воркер после указанного числа запросов, что ограничивает последствия утечек памяти.
- **`request_terminate_timeout`:** останавливает слишком долгие запросы.
- **`request_slowlog_timeout`** и **`slowlog`:** пишут стек вызовов для запросов медленнее порога.

Если на странице статуса `listen queue` больше нуля, а счётчик `max children reached` растёт, все воркеры заняты и запросы ждут. Также включите OPcache с `opcache.validate_timestamps=0` на проде и оптимизированный автозагрузчик Composer. Если воркеры в основном ждут БД или API, помогут дополнительные воркеры. Если CPU загружен на 100%, нужны дополнительные серверы или более быстрый код.

## Лаг репликации

При репликации primary-replica запись идёт на мастер, а чтение распределяется по репликам. Репликация обычно асинхронная, поэтому реплики отстают на миллисекунды, а под высокой нагрузкой — на секунды. Пользователь, обновивший профиль, может прочитать с реплики старую версию.

- **Читать с мастера после записи:** до конца запроса или несколько секунд для этого пользователя. Laravel делает первое через `'sticky' => true` в `config/database.php`.
- **Читать критичные данные с мастера:** балансы, статус заказа после оплаты и данные, на основе которых выполняется следующая запись.
- **Ждать реплику:** MySQL умеет ждать GTID через `WAIT_FOR_EXECUTED_GTID_SET()`, а ProxySQL может направлять чтение только на реплики с небольшим лагом.
- **Полусинхронная репликация:** мастер ждёт, пока хотя бы одна реплика получит запись. Это снижает потерю данных при failover, но увеличивает задержку записи.
- **Мониторить лаг:** `Seconds_Behind_Source` в MySQL и `pg_stat_replication` в PostgreSQL.

## Keyset-пагинация

`ORDER BY id LIMIT 20 OFFSET 1000000` заставляет БД прочитать и отбросить миллион строк, прежде чем вернуть 20. Кроме того, строки, добавленные или удалённые между загрузками страниц, сдвигают результаты.

Keyset-пагинация (пагинация по курсору) продолжает с последнего увиденного значения сортировки. Запросы ниже работают в MySQL 8.0+ и PostgreSQL:

```sql
-- Первая страница
SELECT id, title, created_at FROM posts
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- Следующая страница: значения из последней строки предыдущей страницы
SELECT id, title, created_at FROM posts
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

С индексом по `(created_at, id)` каждая страница стоит одинаково. Сортировка должна быть уникальной, поэтому `id` разрешает совпадения. Перейти на произвольную страницу нельзя, но для бесконечной прокрутки и API это приемлемо. В Laravel для этого есть `cursorPaginate()`. Для выгрузок и пакетной обработки перебирайте строки пачками по первичному ключу, а не через `OFFSET`.

## Соединения с БД

Каждый воркер PHP-FPM держит своё соединение с БД, поэтому число соединений равно числу воркеров, умноженному на число серверов: 20 серверов по 100 воркеров открывают 2000 соединений. PostgreSQL запускает отдельный процесс на каждое соединение и лучше всего работает с несколькими сотнями, а MySQL тоже деградирует на тысячах потоков.

- **Пулер соединений:** PgBouncer для PostgreSQL и ProxySQL для MySQL позволяют множеству клиентских соединений делить несколько десятков реальных. В режиме transaction у PgBouncer состояние сессии — переменные сессии, advisory-блокировки, `LISTEN` — работает ненадёжно.
- **Постоянные соединения** (`PDO::ATTR_PERSISTENT`) экономят время на установку соединения, но их число по-прежнему равно числу воркеров, а состояние, например открытая транзакция, может перейти в следующий запрос.
- **Согласуйте размеры пулов:** не ставьте `pm.max_children` больше, чем может обслужить БД.
- **Долгоживущие рантаймы** вроде RoadRunner, Swoole и FrankenPHP могут держать свои пулы, но должны переподключаться после сбоев и сбрасывать состояние между запросами.

## Очереди и всплески трафика

Очередь разделяет приём работы и её обработку. Во время всплеска веб-серверы принимают запросы и публикуют сообщения, а воркеры обрабатывают их в темпе, который выдерживают БД и внешние API.

- **Доставка at-least-once:** большинство брокеров может доставить сообщение повторно, поэтому консьюмеры должны быть идемпотентными, например дедуплицировать по ID сообщения или опираться на уникальное ограничение.
- **Повторы и dead letter queue:** повторяйте временные ошибки с растущей задержкой, а сообщения, которые падают снова и снова, переносите в отдельную очередь.
- **Глубина очереди:** растущая очередь означает, что консьюмеры не успевают. Добавляйте воркеры автоматически в зависимости от глубины очереди.
- **Порядок:** параллельные консьюмеры не сохраняют порядок. Если порядок важен для сущности, партиционируйте по её ID, например с помощью партиций Kafka.
- **Ограничения:** задайте максимальную длину или TTL и решите, что происходит, когда очередь заполнена.
- **Надёжная публикация:** паттерн Transactional Outbox записывает сообщение в таблицу в той же транзакции, поэтому оно не теряется, если брокер недоступен.

## Подготовка к всплеску трафика

**До события:**

- Проведите нагрузочное тестирование реалистичных сценариев на ожидаемом пике и выше, чтобы найти первое узкое место — обычно это БД.
- Кэшируйте статику и публичные страницы в CDN, а горячие данные — в Redis, и прогрейте кэши до старта.
- Добавьте серверы заранее: автомасштабированию нужны минуты, чтобы среагировать. Проверьте и другие лимиты: соединения с БД, квоты внешних API и лимиты облачного аккаунта.
- Перенесите некритичную работу, например письма и аналитику, в очереди.

**Во время события:**

- Отключите дорогие второстепенные функции, например рекомендации, через feature flags.
- Отсекайте лишний трафик на входе через rate limiting и HTTP 429 или 503 на балансировщике, а не ждите, пока каждый запрос упадёт по таймауту. В крайних случаях можно использовать виртуальную комнату ожидания.
- Защищайте зависимости таймаутами и circuit breaker.
- Следите за долей ошибок, перцентилями задержки, глубиной очередей и нагрузкой на БД.

**После события:** разберите, что сломалось первым, и исправьте это до следующего события.

## Деплой и миграции без простоя

Стратегии деплоя:

- **Rolling:** экземпляры заменяются по одному. Старая и новая версии работают одновременно, поэтому они должны быть совместимы.
- **Blue-green:** деплой в идентичное окружение и переключение всего трафика сразу. Откат — переключение обратно.
- **Canary:** небольшая доля трафика идёт на новую версию, вы смотрите на метрики и постепенно увеличиваете долю.
- **Один сервер:** деплой в новую директорию релиза, атомарное переключение симлинка `current` и перезагрузка PHP-FPM, чтобы OPcache подхватил новый код.

Во время деплоя старый код продолжает работать, поэтому миграции должны быть обратно совместимыми. Используйте паттерн expand and contract, например для переименования колонки:

1. **Expand:** добавьте новую колонку, и пусть код пишет в обе.
2. **Migrate:** перенесите существующие данные пачками.
3. Переключите чтение на новую колонку.
4. **Contract:** в следующем релизе перестаньте писать в старую колонку и удалите её.

Изменения схемы могут блокировать большие таблицы. В MySQL 8 используйте `ALGORITHM=INSTANT` или `INPLACE` либо инструменты online schema change, например gh-ost и pt-online-schema-change. В PostgreSQL используйте `CREATE INDEX CONCURRENTLY` и задавайте `lock_timeout` для миграций.

## Счётчики с большим числом записей

`UPDATE posts SET views = views + 1 WHERE id = ?` на каждый запрос заставляет все транзакции ждать одну и ту же блокировку строки, а БД получает по записи на каждый просмотр.

- **Агрегация в Redis:** на каждый просмотр выполняйте `INCR views:post:42`, а задача по расписанию раз в минуту записывает итоги в БД одной пачкой. Счётчик в БД немного отстаёт, зато число записей резко падает.
- **Шардированные счётчики:** разбейте счётчик на N строк (`post_id`, `shard_no`, `count`), обновляйте случайную строку и читайте сумму. Конкуренция за блокировку снижается в N раз.
- **Журнал событий:** пишите события просмотров в очередь или Kafka и агрегируйте их в консьюмере или аналитической БД, например ClickHouse.
- **Уникальные посетители:** Redis HyperLogLog (`PFADD`, `PFCOUNT`) считает уникальные значения примерно в 12 КБ с погрешностью около 0,81%.

Лайки должны быть уникальными для пользователя и их можно отменить, поэтому источником истины остаются строки `(user_id, post_id)` с уникальным ограничением, а отображаемое число — кэшированное значение.

## Observability

Observability — способность понять, что происходит внутри системы, по её внешним сигналам:

- **Метрики:** числовые временные ряды для дашбордов и алертов, например в Prometheus и Grafana.
- **Логи:** структурированные записи с ID запроса, собранные в системе вроде ELK или Loki.
- **Трейсы:** путь одного запроса через сервисы со временем каждого шага, например с OpenTelemetry и Jaeger.

Полезные методики:

- **RED** для сервисов: rate, errors и duration.
- **USE** для ресурсов — CPU, памяти, соединений: utilization, saturation и errors.
- **Четыре золотых сигнала** из Google SRE: latency, traffic, errors и saturation.

Измеряйте задержку перцентилями (p50, p95, p99). Среднее значение скрывает медленные запросы, которые замечают реальные пользователи. Определите, что вы измеряете (SLI, например долю запросов быстрее 300 мс), и цель (SLO, например 99,9% в месяц). Настраивайте алерты на симптомы, которые чувствуют пользователи, а не на каждый всплеск CPU.

## Нагрузочное тестирование

Распространённые инструменты: k6, Gatling, JMeter и Locust для сценариев и wrk2 для быстрых замеров одного эндпоинта.

Виды тестов:

- **Load test:** ожидаемый пиковый трафик. Укладывается ли система в целевые показатели?
- **Stress test:** нагрузка растёт, пока система не сломается. Где предел и как именно она ломается?
- **Spike test:** резкий скачок трафика. Справляются ли автомасштабирование и кэши?
- **Soak test:** умеренная нагрузка в течение нескольких часов. Выявляет утечки памяти и соединений и растущие очереди.

Практики:

- Тестируйте в окружении, близком к продакшену, с реалистичными объёмами данных. Запрос, быстрый на 1000 строк, может быть медленным на 10 миллионах.
- Моделируйте пользовательские сценарии — просмотр, поиск, добавление в корзину, оформление заказа — с паузами между шагами.
- Следите за p95 и p99 задержки, долей ошибок и пропускной способностью вместе с загруженностью серверов: CPU, `listen queue` у PHP-FPM, соединениями с БД и медленными запросами.
- Некоторые инструменты ждут медленного ответа, прежде чем отправить следующий запрос, и занижают задержку. k6 с arrival-rate executors и wrk2 этого избегают.
- Меняйте что-то одно за раз и сравнивайте результаты.
